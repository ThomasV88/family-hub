# v1.0 gap closure

Three code gaps from the v1.0 milestone integration check, one commit each.

## W1. ai-worker.env provisioning and non-gating deploy

- `scripts/server-provision.sh` now creates `ai-worker.env` (mode 600, keys mirror `ops/env/ai-worker.env.example`,
  `DB_PASSWORD` = the generated `fh_app` password, never printed, never overwritten; an empty placeholder is filled).
- `scripts/deploy.sh` no longer lists `ai-worker.env` in `REQUIRED_FILES`. A missing or empty file logs a warning and every ai-worker
  step (pull, image check, start, rollback restart) is skipped. The mode check in `guard_secrets` still applies when the file exists.
- Decision: compose loads `env_file` for every service, so a missing `ai-worker.env` would break `up app ...` too. deploy.sh creates an
  empty mode-600 placeholder; the steps stay skipped while it is empty and provisioning later fills it.
- Deviation: the provision dry-run test was already failing at HEAD because the generated `app.env` lacked `SESSION_EXPIRE_ON_CLOSE`,
  `MAIL_MAILER`, `GOOGLE_*` and `VAPID_*` keys that `ops/env/app.env.example` has. Added them (empty or log driver) so the key-parity check passes.
- Tests: `scripts/test-server-provision.sh` (mode, content, no secrets, no overwrite, placeholder filled), `scripts/test-deploy-guards.sh`
  (missing and empty file pass guard_inputs and warn). Docs: `docs/ops/server.md`. `scripts/check-compose.sh` needed no change.

## W2. audit:prune cron on provisioned servers

- `cron_block()` adds a monthly line (day 2, 05:40, staging +5 min) running as `deploy`:
  `cd <stack> && IMAGE_TAG="$(cat .last-good-tag)" docker compose -f compose.server.yaml --profile migrate run --rm --no-deps -T migrate php artisan audit:prune >> logs/cron.log 2>&1`.
- `-f compose.server.yaml` because a provisioned `.env` has no `COMPOSE_FILE`; `IMAGE_TAG` from `.last-good-tag` because the compose file
  requires it (same approach as `cert-renew.sh`); project name comes from `.env` in the stack directory. Still not in the Laravel scheduler.
- `ops/cron/family-hub.cron.example` and `docs/ops/server.md` updated; the provision test asserts exactly one such line.

## W3. wishlist manager route recency

- `settings.members.wishlist_managers.update` is now `access:admin` + `access:recent`.
- `SensitiveRoutes`: added to `accessGranting()` with the prefix `settings.members.wishlist_managers.` in `grantPrefixes()`.
- Decision: `settings.members.second_factor.destroy` already had `access:recent`, but a reset lowers an account's protection, so it was
  added to `accessGranting()` and `grantPrefixes()` (`settings.members.second_factor.`) so the net enforces it.
- Decision: `settings.members.sessions.*` stays outside the net and without `access:recent`: listing and revoking sessions only removes access
  and grants nothing, so a revoke without a recent confirmation is defensible. A test pins this.
- Tests: stale admin gets 423 `confirm_required` and no manager rows change, a fresh one saves; the generic access-granting loops now cover
  both routes. The matrix row keeps its fresh-session expectations (comment added); `grantSnapshot()` includes `wishlist_managers`.
