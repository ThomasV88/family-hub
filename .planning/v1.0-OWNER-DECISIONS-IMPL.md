# Owner decisions: implementation notes (2026-11-15)

Implements `.planning/v1.0-OWNER-DECISIONS.md` items UI ("Add task" button), Health decision B (archive instead of delete), WR-12
(image limits) and the GDPR note. One commit per item. Nothing was pushed, no server touched.

## 1. "Add task" button only on Overview, Tasks and Wishlist

- Mechanism: `AppShell` passes whether the current page may use the default add entry to `provideShell({ defaultAdd })`
  (`DEFAULT_ADD_PAGES = ['overview', 'tasks']`, derived from the existing `current` prop). `TopBar` and `FabAdd` show the
  button when `shell.defaultAdd && todo edit` OR when a page registered a labelled handler (`shell.addLabel`). So:
  Overview and Tasks keep the To-do default (Tasks' board registers its own handler), Wishlist and Occasions keep their labelled
  `ShellAdd`, Health person page keeps "Add visit", Finance keeps "Add transaction" while it has accounts. Finance without a
  handler, Settings, Style guide, Forbidden and Confirm access show no add button (the latter two now pass `current=""`).
- Phones: `FabAdd` uses the same rule.
- Tests (Vitest, `tests/js/shell/AppShell.test.js`): 8 new (6 pages x desktop topbar and phone FAB, a labelled handler on Health,
  a labelled handler on Wishlist). `shellState.test.js` unchanged (the `triggerAdd` fallback is kept).

## 2. Health: archive instead of delete after the window

What was built
- `config/medical.php` `delete_window_hours` from `MEDICAL_DELETE_WINDOW_HOURS`, default 72, clamped 0..8760 (0 = always archive);
  `App\Medical\Retention` also clamps at read time. Documented in `ops/env/app.env.example`, mirrored in
  `scripts/server-provision.sh` (provision dry-run test passes), and in `docs/ops/server.md`.
- Migration `2026_11_24_100000_add_archive_columns_to_medical_tables`: `archived_at` (timestamptz) and `archived_by`
  (FK users, `nullOnDelete`, so removing a user never removes a record) on the six tables, plus a partial index
  `WHERE archived_at IS NOT NULL` per table. Existing table grants cover new columns (no grant statement needed).
  Verified with the owner credentials: migrate, rollback --step=1 and migrate again all run clean (the rollback drops both columns).
- Single scope: `Visibility::subjectIds` excludes archived people and `Visibility::apply` adds `archived_at is null` for the five
  record tables (new `ArchiveState` Active/Only/Any, default Active). Everything that already read through the scope (lists,
  switcher, timeline, folders, counts, document list/preview/file/pages, exports in all formats, emergency card, AI run start,
  review, vaccinations list and attention count) is hidden by that one change. Membership-predicate shape is preserved, so the
  privacy arch and leak nets still hold.
- Unscoped system reads fixed explicitly: `SystemQuery` (reminder planning, send-time recheck, display name, AI consent,
  document-to-person lookup), `AiJobQuery` (running job: `abortReason` answers `access` for an archived document or person,
  `document()` and `finishReady` refuse), `AiBulkEligibility` and `AiBulkJobQuery` (never eligible), `AiReviewQuery`
  (accept, reject and undo refuse an archived document; a duplicate-detection match ignores archived records). `AiConsent::allows`
  is false for an archived person.
- Removal: `ArchiveQuery::remove` (records) and `SubjectQuery::remove` (person) replace the old `delete` methods, which are gone
  (so no code path can still delete an old record). The server reads `created_at` under a row lock: inside the window a permanent
  delete (person: with files after commit, as before), otherwise an archive. Controllers keep their routes and flash
  `toast.outcome = deleted|archived`, with message key `health.archive.archived` after an archive.
- Restore: `POST /health/people/{person}/restore` and `POST /health/people/{person}/archive/{type}/{record}/restore`
  (`access:module,health,edit`, throttled, same 403 for everything that misses; type is an allowlist).
- Audit: `medical_archived` and `medical_restored`, meta `subject`, `type`, `record` (ids and an enum only), in the `health` group,
  rendered by `AuditTable` with a type phrase; labels in en/sk/pl.
- UI: person menu entry "Archived items" opens an Archive panel (`?panel=archive`, Edit only, grouped by type, Restore);
  "Archived people" under the switcher (also shown with no active person). Delete dialogs and the trigger button switch to archive
  wording from a display-only `permanentDelete` hint in the props (the server decides again). New keys `health.archive.*` and
  `audit.detail.medical_*` in en, sk, pl with identical key sets.
- Staging: seeded people and records are created 30 or more days in the past (`created_at`), so deletes on staging archive.
  Demo adds one archived visit and one archived document of person A and one archived person (with a visit and an allergy).
  `staging:audit` also fails on `archived_by` of a real user. `docs/ops/staging-data.md` updated. The reseed purge deletes by
  owner regardless of archive state (verified by the existing reseed tests, which now include the archived rows).
- `medical:prune-orphans`: files of archived documents are referenced rows, so they are not orphans; the archived person's
  directory stays. Breaker unchanged. Covered by tests.

PROVISIONAL choices
- Archived documents DO count towards the 200-documents-per-person cap (`DocumentQuery::countStoredForSubject`): the file is still
  stored, so archiving does not free a slot; only a permanent delete inside the window does. Shown counts exclude archived rows.
  The 1000-records cap of the AI accept path was already an unscoped count and so also includes archived records.
- Archiving a person archives it as a whole (one flag on the person, no per-record flags written): everything below it is hidden
  and restoring the person brings back exactly what was active before. Records archived on their own earlier stay archived.
- A document attached to an archived visit reads as unattached (its visit link is kept in the database) until the visit is
  restored; the export carries no reference to an archived visit. Hard-deleting a visit inside the window detaches its documents
  as before.
- An AI suggestion that matches an archived record creates a new active record (it does not link to the hidden one).
- A running AI job of an archived document or person ends as cancelled with reason `access` (the existing constraint has no
  `archived` value; no migration of that constraint was made).
- Window age is `now - created_at` of the row itself (a person is judged by the person's `created_at`, a record by its own).
- The Home health card is a static link with no counts, so there is nothing on the dashboard to filter.
- The admin people list in Settings (membership management, names only) still lists archived people.

## 3. Medical image limits

- Longest edge 3600 px (was 2400), JPEG quality 90 (was 82), thumbnail 480 px unchanged: `config/medical.php`
  (`image_full_px`, `image_jpeg_quality`). `ImageProcessor::process` takes an optional quality and decode budget; the wishlist
  keeps 1280 px and q82. EXIF and GPS are still stripped (re-encode) and no original is kept (only `-full.jpg` and `-thumb.jpg`).
- Memory (PHP 8.4, `memory_limit=128M` as in `docker/app/php-prod.ini`, probe `tests/Support/medical-image-memory-probe.php`):
  a 4032x3024 photo at 3600 px peaks at 89.5 MiB above a 24 MiB baseline, 112 MiB in total, RSS about 141 MiB; the old 2400 px
  output needed about 70 MiB. The old 13 MP input cap alone no longer bounds it (a 3600x3600 image would hold 13 MP twice, about
  114 MB, and die with a fatal error). Result: the input cap stays at 13 MP and a new `medical.image_decode_budget_bytes`
  (106 MB) bounds the estimate `input bytes + 4.4 x (input pixels + output pixels)`; over it the upload is refused as
  unreadable before any decode. A 12 MP phone photo up to about 4 MB passes; near-square images above about 10 MP and 12 MP files of
  close to 10 MB are refused.
- Limit that remains: the app container has `mem_limit` 192m with up to 4 php-fpm children and one decode needs about 141 MiB RSS,
  so a large upload while three other children are busy could get the container killed (decodes are serialized per container).
  Not changed (a server sizing decision): raise `MEM_APP` to 256m or lower `pm.max_children` to 3 if restarts with exit 137 ever
  appear. Documented in `docs/ops/server.md` and `docker/app/php-fpm-prod.conf`.
- Tests: `tests/Unit/Health/MedicalImageLimitsTest.php` 8 tests (config pins, quantizer 90 vs 82, 3600 px cap, no EXIF/GPS, no
  original, no upscaling, budget accept/reject, two 128M probe processes); `DocumentSnifferTest` now pins 3600.
