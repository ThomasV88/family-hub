# Staging demo seed (2026-11-15)

## Goal
The owner can test every module on staging without typing data in: one demo family with about 4 years of history, recreated on every staging deploy. Scenario map for the owner (Slovak): `docs/ops/staging-data.md`.

## Design
`database/seeders/StagingSeeder.php` keeps its three jobs (purge the previous synthetic rows, create the 6 members + admin with the shared password hashed once, call the modules) and delegates to one class per module in `database/seeders/Staging/`:

| Class | Seeds |
|---|---|
| `StagingContext` | "today" in the family time zone, members by role, day-offset helpers (all dates are relative, so data always looks current) |
| `TasksSeeder` | tasks via the model (so the reminder observer computes `remind_at`) |
| `WishlistSeeder` | wishes, urls, occasions, reservations, co-buys, a list manager |
| `FinanceSeeder` | accounts, memberships, bulk-inserted transactions, recurring items and matches, budgets, import profile and batches |
| `HealthSeeder` | people, memberships, visits, medications, allergies, vaccinations, contacts |
| `DocumentsSeeder` | six synthetic files through `MedicalDocumentStore` |
| `AiProposalsSeeder` | ready/failed extractions, decisions, `ai_calls` |

Determinism: faker seeded per locale (names drawn before the user factory consumes the shared random generator), `mt_srand(1201)` in the finance seeder, no other randomness. Two runs on the same day give the same names, task titles and transaction amounts (tested). Row ids (uuids) are random.

Grants: presets unchanged; added Health Edit for parent1 and parent2, Health View for sk_sk.2 and pl_pl.3, Finance View for sk_sk.2, Wishlist View for the Guest (the Guest preset has no wishlist grant, so a list for the Guest would have been invisible). Admin keeps none.

## Timing
`staging:seed --force` on the dev database: 1.1 to 1.3 s in the seeder (about 2.5 s wall including the container start), as `fh_app`, twice in a row. In the test database about 1 s per run. Limit asked for: 60 s (a test asserts it).

## Purge and idempotency
Everything is owned by a synthetic user, so the existing purge by `created_by` / `creator_id` / `owner_id` / `user_id` / `started_by` covers it; cascades remove the children (task members, wish urls, reservations, contributions, managers, finance members/import rows/rejections, medical records, contacts, memberships, documents, extractions, decisions, `ai_notice_acks`). No custom finance category is created (it has no owner column, so a reseed could not remove it); only the migration's defaults are used. `staging:audit` rules are unchanged and still fail on real data (tested).

Two additions to the purge in `StagingSeeder`: the files of the deleted people are removed with `MedicalDocumentStore::deleteSubjectDirectory` after the transaction commits (a rolled-back seed keeps its files), so repeated deploys do not pile up orphan files and trip the circuit breaker of `medical:prune-orphans`. `medical:prune-orphans` remains the safety net.

Tests: `tests/Feature/StagingDemoSeedTest.php` (11 tests: ranges per module, task scenarios, wishlist privacy through the real `/wishlist` page, finance visibility and hidden transfer counterpart, health visibility and vaccination due dates, documents on disk, AI proposals valid against schema v1 and loadable in the review query, no hand-written audit rows, idempotency with no orphans, determinism, audit still flags real data). `tests/Feature/StagingSeedTest.php` updated: `Storage::fake('medical')`, the grants test now expects the four health grants and no admin data, and the reseed tests compare against the baseline counts of a clean seed instead of "tables are empty".

## Limits and decisions
- Factories and plain inserts instead of the query classes: the arch tests keep the medical models and query classes, the finance models and the reservation models out of everything but their layers and the factories (`Database\Factories`). Rather than widen those allow-lists, the seeder uses the factories (medical) and `DB::table` (reservations, finance). Domain constraints still hold through the database (check constraints, composite foreign keys, unique indexes).
- `ai_calls` is append-only for `fh_app`, so each deploy leaves 3 more call rows with ids of deleted demo users (the audit accepts them; `ai:prune-calls` removes them after retention). The idempotency test accounts for it. `audit_logs` is never written by the seed.
- Wishes have no images (no network, no fetch). Links use example.com and are never fetched.
- Single currency (EUR) in finance; wish prices use EUR/PLN/GBP per member. Only default finance categories.
- Vaccination reminders and other notifications are created by the scheduler from the dates; no outbox rows are seeded. `ai_notice_acks` are not seeded, so the AI notice appears on first use.
- If the medical volume is not writable the documents (and so the proposals that depend on them) are skipped with a log warning; the rest of the seed still runs.
- Environment note found while running the full suite: the already running `family-hub-worker-1` and `family-hub-scheduler-1` containers (not part of project `fh1201`) write to the shared `storage/logs/laravel.log`, which had grown to about 289 MB and makes `AiJobLeakTest` run out of memory (it reads every log file). The suite was run with a scratch directory mounted over `storage/logs`. The log was left untouched.
