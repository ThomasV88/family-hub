# Phase 08 — UI Design Contract

> Visual and interaction contract for the AI Extraction Platform: the "Run AI" action and notice, document status states, the side-by-side review screen, the AI-extracted / Unverified / Verified labels, the admin "AI calls" section with Codex login health, empty and error states, and SK/PL/EN copy. Generated by gsd-ui-researcher, verified by gsd-ui-checker.
> Sources: 08-CONTEXT.md (locked), 07-UI-SPEC.md (tokens, `Ui*` components, Health gate behaviour, privacy contract, plural rules: inherited), 07-09 (AI consent, `AiConsent::allows`), 07-14 (documents UI), sketch findings `medical-and-settings.md` (sketch 007/008). Items marked "(discretion)" were decided here. Items marked **PROVISIONAL** are conservative choices the owner may change at the end of the run. No question was asked of the user.

## Privacy and gate contract (inherits 07 entirely)

- Every endpoint (run, cancel, status, review page, accept, edit-accept, reject, undo) is gated server-side by `access:module,health`, per-person Edit scope and the idle/second-factor gate. A hidden or unknown person, document, extraction or entry id returns the same 403 `UiErrorState` as 07 with the single link "Back to Health". Ids are opaque UUIDs; names never appear in URLs, `<title>`, toasts for other people or shared props.
- Consent is the server's decision: `AiConsent::allows` is checked at queue time and again when the job runs. The UI never infers consent from cached props for the final word; a 403/409 from run is rendered as the "AI is off" state without revealing why for hidden people.
- JSON/fetch calls (run, cancel, poll, accept, reject) go through `securityFetch` and 423 maps via `handleHealthRefusal` (07 rules). Nothing is replayed. No review draft is persisted in `localStorage`, `sessionStorage`, IndexedDB or Inertia `remember`; edit-form drafts are component memory only (a gate redirect discards an unsaved edit, and the confirm page's existing alert is the notice). `encryptHistory` stays on for the review page; responses `Cache-Control: private, no-store`; the service worker never caches review pages or status polls.
- The proposal payload is medical content: it is never placed in toasts, logs, `aria-live` text beyond the entry title the viewer already sees, or the admin AI calls table.
- Admin AI calls: admins see person names, member names, agent, model, status, duration and time only. No document name, no content, no count of records, no link to the person page or document (Phase 7 admin rule, still **PROVISIONAL** per 07).

## Screens and Interaction Contract

### 1. "Run AI" action and the one-time notice

Focal point: the "Run AI" button with the always-visible "Sends this document to OpenAI." line beneath it.

- Location: `DocumentPanel` actions area, after "Open in new tab" and "Download document", before the ghost danger "Delete document". Not on timeline rows (rows show only the status tag). Hidden for view-only members (no disabled ghost, no explanation, they see only the status tag and, when ready, nothing else: review needs Edit).
- Button states:
  - Available: secondary "Run AI" (`Sparkles`). Enabled when consent is on, no run is queued/running, and the Codex login is not known to be expired.
  - Consent off (state "consent switched off"): button has `aria-disabled="true"` (focusable, press does nothing but announce) and a visible line below it (not a tooltip): "AI is off for this person. Turn it on in the person header to run AI." with link "Go to person header" (focuses the `AiConsentControl` switch). Applies even when earlier suggestions exist.
  - Login expired or worker down (known from the stored health state): `aria-disabled` plus line "AI is not available right now. Ask a family admin to check the AI settings." (no technical detail for non-admins; **PROVISIONAL**, shown to every editor).
  - Queued or running: button replaced by secondary "Cancel run" (`Ban`); status block shows the tag.
  - Ready: primary "Review suggestions" (link to the review page) and ghost "Run AI again" (opens the same flow; creates a new run and supersedes the old one on success of queueing). Starting a re-run while unreviewed suggestions exist asks for plain confirm "Replace these suggestions?" body "Running AI again replaces the suggestions you have not reviewed. Entries you already added to the record stay." buttons "Run AI again" (default, not danger, because nothing saved is lost) / "Keep current suggestions" (default focus).
- One-time notice (`AiNoticeDialog`): shown on the first "Run AI" press by a member, stored server-side per member ("notice acknowledged", **PROVISIONAL**: per member, not per person; the dialog does not reappear for other documents or people; the permanent line under the button covers every later use). Title "Send this document to OpenAI?". Body "This document will leave this server and be sent to OpenAI to be read. OpenAI may keep it under its own terms. You will check every suggestion before anything is saved. You will only see this notice once." Buttons: primary "Run AI" (accent), safe secondary "Cancel" with default focus. Esc and backdrop equal Cancel. Confirm queues the run in the same request that records the acknowledgment (one audited action). 
- After queueing: dialog closes, toast "AI run started", status block shows "Waiting for AI", focus returns to the "Cancel run" button.
- Run errors (inline `UiAlert` danger under the button, `role="alert"` once): queue failed "We could not start the run. Nothing was sent. Try again."; consent turned off between click and server check: switch to the consent-off state above, no error alert.
- Cancelling: "Cancel run" calls cancel immediately (no confirm; nothing is lost). Toast "Run cancelled". If the process already started, the status stays "AI is reading" until the worker confirms the kill, then becomes "Cancelled". Copy never claims nothing was sent after a start.

### 2. Status states on the document

Focal point: the status tag with one next action.

Shown in `DocumentPanel` (tag, detail line, next action) and as a tag on the document's row in timeline and folder lists (tag only, hidden when there is no run or the run is superseded by a ready run).

| State | Tag | Detail line (14/400 muted) | Next action |
|-------|-----|----------------------------|-------------|
| No run | none | none | "Run AI" |
| queued | Waiting for AI | "This usually takes a few minutes. You can leave this page." | "Cancel run" |
| running | AI is reading | same line | "Cancel run" |
| ready | Suggestions ready | "{n} suggestions to review." (pipe plural; zero uses the Empty state of Screen 3, tag text then "Nothing to suggest") | Primary "Review suggestions" |
| failed | AI could not read this | "AI could not read this document. Nothing was saved. Try again, or add the details by hand." | "Run AI again" |
| cancelled (user) | Cancelled | "This run was cancelled. Nothing was saved." | "Run AI" |
| cancelled (consent off) | Stopped: AI is off | "AI is turned off for this person. This run was stopped." | consent-off state of Screen 1 |
| superseded | Replaced by a newer run | shown only on a directly opened old review page (Screen 3), never on the document | link "Open newest suggestions" |
| consent switched off (no run) | none | consent-off line of Screen 1 | none |

- Failure copy is generic on purpose (content-free, same for validation failure, timeout, CLI error). A failed run never shows a partial proposal.
- Updates: while queued or running the panel and the list tag poll by Inertia partial reload (`only` the document status props) every 5 seconds, backing off to 15 seconds after 2 minutes, paused when the tab is hidden (resumes on `visibilitychange`), stopped on any terminal state, and stopped after 15 minutes with the line "Still waiting. Reload the page to check again." (**PROVISIONAL**: polling chosen over push per Claude's discretion). A 423 during polling goes through `handleHealthRefusal`. A poll error keeps the last state and shows nothing; three consecutive errors show inline "We could not check the status. Check your connection." with ghost "Try again".
- Announcements: only state transitions are announced, via a single `role="status"` region (polite): "AI is reading this document.", "Suggestions are ready.", "AI could not read this document.", "Run cancelled." Polls that change nothing announce nothing. `aria-busy="true"` on the status block while queued/running; the `Loader` icon is `aria-hidden` and static under reduced motion.
- Loading (first paint): `UiSkeleton` of tag height; no layout jump when the tag arrives.

### 3. Review screen (`AiReviewPage`)

Focal point: the suggestion currently needing a decision (first pending entry), because the user's job is a sequence of per-entry decisions against the document.

Header region (always visible above the panes): ghost link "Back to document" (opens the person page with `?panel=document&id=`), h1 "Review AI suggestions", muted line with the status tag "Suggestions ready" and the run date (`<time>`, locale medium date and time), progress line "{n} suggestions left" (pipe plural; "All suggestions handled" at zero), and a `UiAlert` info (not `role="alert"`, always visible): "These suggestions were made by AI and may be wrong. Nothing is saved until you accept an entry. Check each one against the document."

Layout:

- Content width >= 800px (desktop and iPad landscape): two panes side by side, 24px gap, document pane on the start side (flexible, 50%), suggestions pane on the end side (flexible, 50%). Document pane sticky with independent scroll; suggestions pane scrolls with the page. Both panes are `<section>` with an h2 ("Document", "Suggestions"). Pane toggle is not rendered.
- Content width < 800px (phone, iPad portrait): single column with `ReviewPaneToggle` ("Document" / "Suggestions") under the header, default "Suggestions". Both panes stay mounted (`v-show`, `hidden` attribute on the inactive one) so an open edit form and focus are never lost on toggling. Toggle is `role="radiogroup"` with arrow keys, backed by `?pane=`. Switching moves focus to the pane's h2 (`tabindex="-1"`) and announces nothing extra. A layout switch across the threshold (rotation) keeps scroll position per pane and the open edit form.
- 320px and 200% zoom: no horizontal scroll; entry actions wrap; table-free.

Document pane (`DocumentPane`):

- Image: `<img>` of the authenticated derivative, `alt` = document name, fills pane width, `object-fit: contain`, on a `--color-surface-2` frame. Same `onerror` recovery as 07 ("The preview could not be loaded." with "Confirm it's you" and "Try loading again").
- PDF (**PROVISIONAL**): page images from a server derivative route (the image already ships `pdftoppm`), one page at a time, with pager "Previous page" / "Next page" buttons (44px, `ChevronLeft`/`ChevronRight`, disabled at the ends) and a status line "Page {n} of {total}" (`role="status"`). If the plan does not deliver the derivative, the fallback is the 07 PDF file card with "Open in new tab" and the line "Open the document in a new tab to compare." (the stacked toggle then hides nothing useful, so the owner should accept the derivative). HEIC without decode: the 07 "No preview" card.
- Zoom: browser pinch/zoom only; no custom zoom controls. Click on the image opens "Open in new tab" (anchor `target="_blank" rel="noopener"`), as in 07.

Suggestions pane (`SuggestionList`):

- Optional first block "Suggested details" (only when the proposal carries document date and/or specialty): read-only lines "Document date: {date}" and "Specialty: {name}" (specialty from the 07 taxonomy). No accept action: these are context only (**PROVISIONAL**, conservative: the schema fields are not written anywhere in Phase 8).
- Then `<section>` per record type that has entries, fixed order: Visits, Medications, Allergies, Vaccinations; each h3 with count (pipe plural `health.ai.review.count`). Types without entries are omitted. Within a type, document order of the proposal.
- `SuggestionEntry` = `UiCard` (`<li>` of a `<ul>`, `role="group"`, `aria-labelledby` = title id) with: type icon (20px) + title (16/600: visit = doctor or specialty or "Visit"; medication name; allergy substance; vaccine), state tag (Entry pending / accepted / rejected), a `<dl>` of the proposed fields as read text (labels 14/600, values 16/400, using the same field labels as the 07 forms; empty fields are omitted, not shown as dashes), and the action row (wraps, 8px gap, each 44px): secondary "Accept", secondary "Edit", ghost "Reject". Order is always Accept, Edit, Reject.
- Plain text only: model output is rendered with text interpolation, never HTML or markdown, including `aria-label`s and toasts.
- Accept: calls the server, which runs the 07 record query with the entry values (same scoping, validation, audit, AI-extracted provenance, Unverified until verified). Success: entry state becomes "Added to the record" with link "Open in record" (opens the matching 07 panel via query params), actions replaced by that link, toast "{Record} saved" (noun-bearing, no names: "Visit saved", "Medication saved", "Allergy saved", "Vaccination saved"). There is no undo here; the record is deleted through its normal panel. Entries whose values fail 07 validation (for example allergy without severity, vaccination without date) do not Accept silently: Accept opens the edit form with the offending fields flagged "{what is wrong}. {how to fix}." (for example "Choose a severity to add this allergy.").
- Edit: expands the card in place into the 07 field set for that type (reuse the form field components and validation of `VisitPanel`, `MedicationPanel`, `AllergyPanel`, `VaccinationPanel`; visit Documents section is omitted, the visit is automatically linked to this document on accept). Footer: primary "Save {record}" (adds to the record, same as accept with edited values), secondary "Cancel". Dirty cancel opens "Discard changes?" ("Discard" danger / "Keep editing" default focus). An edited and saved entry shows the tag "Added to the record" and the detail line "You edited this suggestion." Only one entry may be in edit at a time per pane; opening another asks nothing if clean, and moves the dirty one to the discard confirm.
- Reject: marks the entry rejected (nothing touches the record), tag "Rejected", the entry collapses to title plus tag, actions replaced by ghost "Undo" (`Undo2`) which restores "Not reviewed yet". No confirm dialog (reversible). Rejection decisions persist on the proposal; they hold no new medical content.
- Optimistic UI: none for Accept and Save (wait for the server, `aria-busy` on the entry, buttons disabled); Reject and Undo update after the response too (consistency over speed, calls are small).
- Completion: when nothing is pending, a `UiAlert` success (`role="status"`) "All suggestions are handled." with links "Back to person" and "Back to document". The page does not auto-navigate.
- Empty proposal (valid JSON with zero entries): `UiEmptyState` (icon `ListChecks` muted 32px) heading "Nothing to suggest", body "The AI found no visits, medications, allergies or vaccinations in this document. You can add details by hand.", action "Back to document" (secondary).
- Superseded extraction opened directly (`?extraction=` old id, or Back-button history): banner `UiAlert` warn "A newer run replaced these suggestions." with link "Open newest suggestions"; entries are read-only (no Accept, Edit, Reject; already-added entries keep "Open in record"). Failed, queued, running or cancelled extraction opened on the review route: redirects to the document panel; if the run is queued/running the page shows the Screen 2 status block instead of panes.
- Consent switched off while the review page is open: reviewing continues (data is already on the server, nothing leaves it). A muted line under the header says "AI is off for this person. You can still review these suggestions." (**PROVISIONAL**.) Accept still works as it is an ordinary record write needing Edit access.
- Loss of Edit access while the page is open: the next action returns the standard 403 state; no partial state shown.
- Error states: load failure `UiErrorState` "Something went wrong" with "Try loading again"; per-action failure inline `UiAlert` danger in the entry (`role="alert"`, once) "We could not save this. Nothing was added. Try again." (entry stays pending, buttons re-enabled); 423 per gate rules; a duplicate action (double click, second tab) returns the server's current state and the entry shows its real state without an error.
- Loading: `UiSkeleton` of two panes (document block fixed to the pane height, three entry cards).

Keyboard and screen reader behaviour (contract):

- Tab order: header link, pane toggle (when stacked, one Tab stop, arrows inside), a visually hidden "Skip to suggestions" link (first focusable on wide layouts only, targets the suggestions h2), document pane (pager buttons, "Open in new tab"), then the suggestion entries top to bottom, within each entry Accept, Edit, Reject. No `tabindex` greater than 0. Enter and Space activate buttons; Enter in edit forms does not submit (07 rule); Esc cancels the edit form (dirty confirm applies) and closes dialogs. No custom shortcut keys.
- Structure announced: landmarks via `<main>`, h1 "Review AI suggestions", h2 "Document", h2 "Suggestions", h3 per type with count (for example "Medications, 2 suggestions"). Each entry is announced as a group named by its title, with its state tag as the first described text ("Ibuprofen, Not reviewed yet"). Buttons carry unique accessible names: "Accept medication {title}", "Edit medication {title}", "Reject medication {title}", "Undo reject for medication {title}" (title is the proposed text, escaped; if the title is empty the type word alone is used).
- Focus management: after Accept or Save, focus moves to the next pending entry's Accept button, or to the completion alert (`tabindex="-1"`) when none is left; after Reject focus stays on the same entry, moving to its Undo button; after Undo focus moves to that entry's Accept button; opening Edit focuses the first field; cancelling Edit returns focus to the entry's Edit button; switching the pane toggle moves focus to the pane h2. Focus is never lost to `<body>`.
- Live announcements (single polite `role="status"` region, text only, no medical content beyond the entry title already focused): "{Record} added to the record. {n} suggestions left.", "Suggestion rejected. Undo is available.", "Rejection undone.", "All suggestions are handled." Errors use one `role="alert"`.
- The `<dl>` fields are read in label-value pairs; state is never carried by color alone (tag text plus icon); `aria-busy` on the busy entry; the document `<img>` has `alt` = document name and the PDF page status line is announced politely.
- Reduced motion: expand/collapse of entries and edit forms uses height/opacity 150-200ms, disabled under `prefers-reduced-motion`.

### 4. AI-extracted, Unverified and Verified labels

Focal point: the pair of tags on a record row, so a clinician can tell at a glance that an item came from AI and nobody has confirmed it.

- Every record created by accept or edit-accept carries `ProvenanceTags` wherever 07 shows that record: side-card rows (medications, allergies, vaccinations), timeline entries and folder entries (visits), the record panel header, and the export screen. Display rules:
  - AI-origin and not verified: "AI-extracted" (neutral, `Bot`) + "Unverified" (warn, `TriangleAlert`).
  - AI-origin and verified by a member: "AI-extracted" + "Verified" (success, `Check`). "Verified" replaces "Unverified"; "AI-extracted" stays permanently as provenance.
  - Human-created records: no provenance tag (unchanged from 07; there is no "Human" tag).
- Verify action: reuse the 07-16 verify action and its copy inside the record panel (secondary "Mark as verified", needs Edit). If 07-16 shipped a different label, 07-16 wins; this spec only adds the "AI-extracted" and "Verified" tag texts. Verifying is a plain save (no dialog), toast "Marked as verified", audited by the existing events. Editing an AI-extracted record does not auto-verify it.
- Row layout: tags sit on their own line under the record's meta line (wrap, 8px gap, 44px row height unaffected). The tags are never the only distinguishing mark in print views: the print export prints the words "AI-extracted, Unverified" as bordered text (07 print rules).
- Severity tags (allergy) keep priority position; provenance tags always come after them.
- Export rule (unchanged from 07): the "Include AI-suggested data nobody has checked yet" checkbox now appears when the person has unverified AI records; copy is the 07 copy.

### 5. Admin "AI calls" section (Settings)

Focal point: the table of calls, with the login-health card above it answering "is AI working at all".

- Placement: new `UiCard` section "AI calls" on the Settings area, admin-only, after the existing AI-related or Members sections (no existing AI settings section exists yet; **PROVISIONAL**: a sibling of other admin sections, nav entry text "AI calls", heading h2 "AI calls"). Non-admins get the standard 403 for the route and no nav entry. Not gated by Health module access: admin role only (consistent with Phase 7 settings access admin).
- Intro line (14/400 muted): "Every time AI reads a document, it is listed here. The list shows who started it and when, never what was in the document."
- `AiLoginHealthCard` (`UiCard`, h3 "Codex login"): status tag (see Color table), line "Last checked {datetime}" (`<time>`, locale), secondary "Check again" (`RefreshCw`, `aria-busy`, disabled while a check is running; the check is queued to `ai-worker`, the card polls every 3 seconds for up to 30 seconds, then shows "No answer yet. Try again later."). Per state:
  - Logged in: success tag only.
  - Login expired: danger tag plus `UiAlert` danger (not `role="alert"` on load, page content): "Codex needs to be signed in again. This cannot be done from this page. Ask whoever runs the server to sign in again on the server." No login form, no token field, no credential is ever shown or accepted in the UI.
  - Worker not responding (no recent heartbeat): warn tag plus line "The AI worker is not running. Members cannot run AI until it is back."
  - Not checked yet: neutral tag plus line "Press Check again to test the login."
  - Also names the one agent: line "Agent: OpenAI Codex. More agents and their order come later." (**PROVISIONAL**; removed by Phase 9, no disabled agent-order controls are drawn).
