## Contracts this plan creates

- `App\Finance\Viewer` (final readonly): `user` (User), `level` (AccessLevel), `canEdit(): bool`, `userId(): int`; `static for(User $user): self` resolves AccessGate from the container and aborts 403 when the finance level is None (so a query class can never run for a user without finance access).
- `App\Finance\Visibility`: `accountIds(Viewer $v)` returns a query-builder subquery `select account_id from finance_account_members where user_id = ?`; `apply($query, Viewer $v, string $column = 'account_id')` adds `whereIn($column, accountIds($v))`.
- `App\Finance\Queries\AccountQuery`: `visible(Viewer): Collection` (ordered by lower(name), id), `findVisible(Viewer, string $id): ?FinanceAccount` (returns null for non-UUID strings without querying), `visibleIds(Viewer): list<string>`, `balances(Viewer, string $asOfDate): array<string,int>` (account id => opening_balance_minor + SUM(amount_minor where booked_on <= asOf)::bigint), `currencies(Viewer): list<string>` (currencies of visible accounts ordered by visible-account count desc then code asc).
- Leak-net area file contract (`tests/Support/FinancePrivacy/<area>.php` returns an array, every key optional):
  `visible` => fn (array &$ctx): void (seed data on the visible account, store ids in $ctx),
  `hidden` => fn (array &$ctx): void (seed canary data on the hidden account, store ids in $ctx['hidden']),
  `params` => [paramName => fn (array $ctx): string] (visible values for route params),
  `hiddenParams` => [paramName => fn (array $ctx): string] (hidden-record values for write parity),
  `panels` => [routeName => fn (array $ctx): list<array<string,string>>] (extra query-string variants per GET surface),
  `payloads` => [routeName => fn (array $ctx): array] (request body for write parity and the visible-write mutation check).

## Mutation scope rule (blocker fix: no write may touch an account the editor cannot see)

- Account-owned finance tables: finance_transactions, finance_recurring, finance_recurring_matches, finance_match_rejections, finance_import_batches, finance_import_rows; finance_budgets is treated the same way (its scope is the set of currencies of the viewer's visible accounts).
- Existing rows of these tables are changed only through App\Finance\Queries methods whose UPDATE/DELETE statement itself carries the membership predicate for the target row's account (e.g. `UPDATE finance_transactions ... WHERE id = ? AND account_id IN (<Visibility::accountIds>)`), so a hidden target row matches zero rows. Writers outside App\Finance\Queries create rows with `new` + forceFill + save and never call `->update(`, `->delete(`, `->forceDelete(`, `->increment(`, `->decrement(`, `->updateQuietly(`, `->deleteQuietly(` or `->save()` on a loaded existing finance model.
- Allowlist (explicit, each with a docblock reason; the scan test holds the exact list): `CategoryQuery::reassign` (family-wide category maintenance by design: UI-SPEC "Deleting a category requires a move target"; returns nothing, responses identical with or without hidden usage), `ImportQuery::pruneDrafts` (scheduler, no viewer). DB-side FK cascades are not statements and are out of scope.
