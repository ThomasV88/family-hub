## Rules

- Occurrences: OccurrenceWindow::dueDates(recurring, from, to) = RecurrenceEngine::between(rule, LocalTime::at(starts_on, '12:00', family tz), max(from, starts_on), min(to, ends_on ?? to), tz) mapped to 'Y-m-d' (decision "anchored 12:00 local"; Schedule mode only, Completion mode is never exposed).
- An unmatched occurrence with due date before schedule_effective_from is not shown; an unmatched occurrence older than today minus config finance.recurring.overdue_lookback_days (45) is not shown; matched occurrences are always shown (from their match rows).
- Status = StatusResolver::resolve(occurrence, matched candidate or null, today in family tz). Match rows are read together with their transaction through the visibility scope (the transaction is always on the same account, so it is visible whenever the recurring item is).
- Create: schedule_effective_from = starts_on. Update: when rule, starts_on or expected amount changes, schedule_effective_from = today (decision); name, category, hints, ends_on changes keep it.
- Delete: removes the recurring item and its match/rejection rows (FK cascade); recorded transactions stay. Updates and deletes of existing recurring rows go through RecurringQuery::updateVisible(Viewer, id, attributes) / deleteVisible(Viewer, id), whose statements carry `account_id IN (<Visibility::accountIds>)` (mutation scope rule from 05-04); RecurringWriter never calls ->update()/->delete()/->save() on a loaded row.
- account_id (and `kind`, which recurring items do not have but which is refused for symmetry with transactions) is IMMUTABLE after creation (plan-revision decision): a PATCH containing `account_id` or `kind` returns 422 with finance.error.immutable on that key whatever the value; hidden and unknown ids give byte-identical bodies. Same-account matching is additionally DB-enforced: finance_recurring has UNIQUE(id, account_id); finance_recurring_matches and finance_match_rejections carry account_id with FOREIGN KEY (recurring_id, account_id) REFERENCES finance_recurring (id, account_id) ON DELETE CASCADE and FOREIGN KEY (transaction_id, account_id) REFERENCES finance_transactions (id, account_id) ON DELETE CASCADE (target constraint finance_transactions_id_account_unique from 05-04).
- Tolerance input: blank or a zero string ('0', '0,00', '0.00') means 0; otherwise MoneyParser::manual in the account currency. window_days must be in config finance.recurring.window_days_options.
- Recurrence input follows the Phase 3 task request format (copy the RecurrenceFields payload handling from StoreTaskRequest: pattern fields -> RecurrencePattern -> RuleBuilder::toRrule); a 'mode'/'repeat from' field is ignored.
