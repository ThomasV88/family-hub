## Color

Reuse 01.1 values. 60/30/10: dominant `--color-bg`, secondary `--color-surface` (cards, panels, rows, calendar cells) and `--color-surface-2` (table header, selected day, track), accent `--color-primary`, destructive `--color-danger`.

Accent reserved for (subset of the 01.1 closed list plus the single-series chart allowance):
1. Primary button, one per view region: "Add transaction" (toolbar and empty state), "Save transaction", "Save account", "Save category", "Save budget", "Save recurring expense", "Record payment", "Read file", "Preview rows", "Import {n} transactions", "View transactions", "Add account" (empty state)
2. FAB on phone ("Add transaction", Overview and Transactions tabs only)
3. Selected account chip, selected view-switch chip (Calendar/List, 6/12 months), selected kind chip in transaction form, selected tab underline, checked checkbox/radio, switch ON
4. Focus ring, text links ("Open recurring", "This month", "Open transaction", "Edit recurring expense")
5. Selected nav item "Finance"
6. Chart data series only: the category bars, the balance line and its markers, and the budget progress fill. One hue, never a second hue for categories

Not accent: amounts, status tags, calendar day cells and today marker, track, filter chips, import step indicator (current step uses `--color-surface-2` fill plus semibold plus `aria-current="step"`), row hover, tags.

Semantic tags (always text plus icon, `UiTag` variants only):
- Upcoming: `neutral` + `Clock`
- Paid: `success` + `Check`
- Overdue: `danger` + `AlertCircle`
- Paid differently: `warn` + `AlertTriangle`, plus a detail line "Paid {actual} on {date}, expected {expected}." in 14/400 muted (the difference is stated in words and numbers, never only by colour)
- Over budget: `danger` + `AlertCircle`, text "Over budget by {amount}" (amount supplied by the server, never computed in the UI)
- Nearly used up (budget >= 90% and <= 100%): `warn` + `AlertTriangle`
- Imported: `neutral`; Possible duplicate: `warn` + `Copy`; New (import): `success` + `Check`; Cannot be read: `danger` + `AlertCircle`
- Below zero (negative balance caption): `warn` + `AlertTriangle`

### Chart colour use (contrast and not colour alone)

- All chart marks use CSS variables, never literal hex, so light and dark both apply: bars and line `var(--color-primary)` (5.27:1 on `--color-surface` light, 6.26:1 dark, both above the 3:1 non-text minimum); track `var(--color-surface-2)` (decorative, values are in text); "Other categories" bar `var(--color-border-strong)` (3.4:1 light); gridlines and zero line `var(--color-border)` / dashed `var(--color-border-strong)`.
- No chart encodes meaning by colour: bar rows carry the category name and amount and percentage as text; the balance chart is one series (no legend), the last point, the lowest and the highest point carry text labels with value; negative values carry U+2212 and sit below a labelled zero line.
- Over-budget is never shown only by the fill turning `--color-danger`: the row also shows the `danger` tag with icon and the exact over amount.
- Every chart has a table alternative (see Charts); chart text is >= 14px at `--color-text` or `--color-text-muted` (4.86:1).
- Forced-colors and print: marks get `stroke: currentColor` fallback via `@media (forced-colors: active)`.

Destructive (`--color-danger`) reserved for: "Delete transaction", "Delete recurring expense", "Remove budget", "Delete category", "Undo import", "Discard" and "Leave import" confirm buttons, field errors, Overdue and Over-budget tags, unreadable import rows.

## Money display (applies to every screen)

- Exact amounts: always the currency's full fraction digits (EUR/PLN/CZK/USD/GBP: 2). No whole-euro rounding anywhere, including summary cards and charts labels (sketch showed whole euros; superseded by the exact-amounts requirement). Balance chart axis ticks use exact formatted amounts (never compact or rounded forms such as "1.2k"); crowding is solved by thinning labels, not by rounding.
- Format through `Intl.NumberFormat` in the active locale (en-GB `€1,234.50`, sk-SK `1 234,50 €`, pl-PL `1234,50 zł` per CLDR); never hand-assembled strings. Amounts arrive as integer minor units plus ISO code; the UI never sums; all sums come from the server per currency.
- Sign: expenses and negative balances show U+2212 (not hyphen) directly attached to the number; income and positive changes show "+" in lists and table alternatives; summary-card income shows no sign (the card title says Income). Every transaction row also has a kind icon (`ArrowDownLeft` income, `ArrowUpRight` expense, `ArrowLeftRight` transfer) with `aria-label` of the kind; amounts stay `--color-text`. Negative/positive therefore never depends on colour.
- No conversion. Different currencies are never added together: wherever more than one currency is in scope (All accounts with mixed currencies) Overview, summary cards, still-to-pay and charts render one block per currency, headed by the ISO code (Heading 20/600). A block exists only if at least one account visible to the viewer uses that currency. Order uses the viewer's visible data only: most used among the viewer's VISIBLE accounts first (count of visible accounts per currency), ties broken alphabetically by ISO code. Nothing about hidden accounts influences presence or order.
- Money inputs: `inputmode="decimal"`, accept comma or dot, ignore spaces and NBSP as thousands separators, always positive (kind chooses direction; opening balance may be negative via explicit leading minus), parsed to integer minor units by `parseMoney` with string arithmetic; currency shown as a read-only suffix taken from the account. Validation message states the allowed decimals.
- Money text is never truncated; long amounts wrap below the label rather than ellipsize.

## Privacy contract (applies to every screen)

A viewer who cannot see an account must get an app that behaves exactly as if that account did not exist.

- The server returns only visible accounts and only data from them: transactions, balances, totals, recurring expenses, occurrences, budget progress, chart data, import history, import duplicate detection, recurring auto-match, match candidates, still-to-pay (module and Home card). Aggregates are computed per viewer from visible accounts only; there is no "hidden" bucket, no "other accounts" line, no lock icon, no counts of anything hidden, and no hint text such as "only counts accounts you can see".
- Public ids for accounts, transactions, recurring items, budgets and imports are opaque (ULID/UUID); no sequential ids, so gaps reveal nothing. `?account=`, `?acct=`, `?tx=`, `?rec=`, `?bill=`, `?budget=` use them. Unknown or hidden ids in these params and `?day=` render the same 403 `UiErrorState` as module access none (Phase 2), identical for non-existent ids (no existence leak).
- Transfers: a transfer whose counterpart account is hidden from the viewer is shown on the visible side as a plain Income (money in) or Expense (money out): ordinary kind icon (`ArrowDownLeft`/`ArrowUpRight`), no counterpart wording, no "another account" text, no transfer icon, the normal category, and it counts in Income/Spending like any such entry. The counterpart name, currency, amount and the fact that it is a transfer are never sent. Only a transfer whose both accounts are visible renders as a transfer. Transfer form account selects list only visible accounts.
- Admin visibility: admins see account METADATA only (name, type, currency, visibility checkboxes) on the Accounts management screen, so they can configure visibility. Balances, transactions, aggregates, charts, chips and every other screen include an account for an admin only if it is shared with that admin (the admin must be ticked like anyone). The sharing line ("Visible to {n} members") and the visibility chooser exist only in `AccountList`/`AccountPanel` for users allowed to manage accounts; other viewers' components have no slot for them. Non-admins see no restricted/private marker.
- Empty state for a member who sees zero accounts is the same copy whether no accounts exist or none are shared ("No accounts to show"). Such a viewer's toolbar, tabs and "Add transaction" are hidden; the page equals a family with no accounts.
- Categories (names) are a family-wide, non-sensitive list by design and appear for everyone with finance access, including categories used only by hidden accounts; they therefore never act as privacy canaries. The list carries no counts or usage data (counts would leak hidden spending). Deleting a category requires a move target and states no counts.
- Budgets are per category. Budget progress counts only transactions from accounts visible to the viewer, so the same budget row may show different numbers per viewer; there is no hint text. "Over budget by {amount}" is computed and sent by the server; the UI never computes it.
- Import duplicate detection and recurring auto-match run only against the selected, visible account (and visible recurring items); a hidden account's transactions never influence status, tags or match candidates.
- Removing a member from an account's visibility takes effect on their next request (403 or filtered result); no live notice.
- Nothing from finance is cached by the service worker; all routes `no-store`; Inertia props carry no ids of invisible accounts.
- Tests (Pest + Vitest): differential test per screen (Overview, Transactions, Recurring, Accounts, Import, Home card): two viewers, one with account X shared and one without; assert the without-viewer's Inertia props and rendered DOM equal those of a fixture family where X never existed (the fixture family may contain a transfer between X and a visible account, which must equal a plain income/expense entry for the without-viewer; currency block presence and order, budget numbers and Over-budget amounts are computed from visible accounts only; import duplicate flags and recurring auto-match results for the visible account ignore X; ids are opaque). Canary strings are an account name, payee or description, never a category name (categories are family-wide by design); canaries never appear in any response or DOM for the without-viewer, including chart table alternative, `aria-label`s, filter option lists, import account select, transfer selects, match candidates and toasts. Admin test: an admin not ticked on X sees X's metadata only on the Accounts screen (no balance) and nothing of X elsewhere.

## Screens and Interaction Contract

Routes (Inertia pages, all `no-store`): `/finance` (Overview), `/finance/transactions`, `/finance/recurring`, `/finance/accounts`, `/finance/categories`, `/finance/import`. Nav entry "Finance" (`Wallet`) in `modules.js`. Panels via query params listed above. Home gets `HomeStillToPayCard`.

### Shell and toolbar (all finance routes)

Focal point: the account chip row with the selected chip, because every number below depends on which accounts and month are selected.

Region order (16px gap): h1 "Finance" with ghost links "Accounts" and "Categories" at the end edge (links only shown to users who may open them; Accounts is visible to everyone with finance view and read-only for non-admins), then toolbar (chips, month switcher, actions), then route-backed `UiTabs` (Overview / Transactions / Recurring; selecting navigates and keeps `?account` and `?month`; tab panel `role="tabpanel"` labelled by its tab), then the tab content.

- Actions: secondary "Import CSV" (leading `Upload`) and primary "Add transaction" (leading `Plus`) at container width >= 640px on the toolbar end edge; phone: "Import CSV" stays in the toolbar row, "Add transaction" becomes the FAB (Overview and Transactions only). View-only users (finance `view` grant) see neither action nor FAB, and a muted line "You can view finance but not change it." under the tabs.
- Changing chip or month does an Inertia partial reload; the content region shows `aria-busy="true"` and keeps previous data dimmed until the new data arrives (no layout jump); `MonthSwitcher` label announces the new month.
- Loading (first load): `UiSkeleton` rows matching the tab layout. Error: `UiErrorState` "Something went wrong" with load body and "Try again". Module access none: Phase 2 403.

### 1. Overview (`/finance`)

Focal point: the "Still to pay" card, the only card with a call to action, answering what must be paid next, with the three summary cards above it giving context.

Order (per currency block, 16px gap): `SummaryCards`, `StillToPayCard`, `BudgetList`, `SpendingByCategoryChart`, `BalanceChart`.

- `SummaryCards`: grid of 3 `UiCard`s at content width >= 560px, stacked below. Each: label (Label 14/600 muted), amount (Display 24/600, `MoneyAmount`). "Balance at month end" is the sum of opening balances plus all transactions to the end of the selected month; when negative it adds the "Below zero" warn tag. Income and Spending exclude transfers.
- `StillToPayCard`: heading "Still to pay"; sum (Display 24/600) of unpaid occurrences for the selected month (Overdue plus Upcoming); caption "{n} payments" and, when > 0, danger tag "{n} overdue"; up to 3 next payments as `UiListRow`s (name, due date, amount, `StatusTag`), each opens `?bill=` on the Recurring tab; link "Open recurring". Empty: "Nothing left to pay this month." (no card actions). If the viewer has no visible recurring items the card is still shown with the empty copy only when recurring items exist for them; if none exist for the viewer, the card is omitted (indistinguishable from none existing).
- `BudgetList` card: heading "Budgets", end-edge secondary "Add budget" (edit users). Row (min 56px): category name (Body 600), text "{spent} of {budget}" (14/400, end edge), `UiProgress` (fill accent, capped at 100% width, `role="progressbar"` with `aria-valuenow` as percent and `aria-valuetext` "{spent} of {budget}"), caption "{n}% used". At > 100%: fill `--color-danger`, tag "Over budget by {amount}"; 90 to 100%: warn tag "Nearly used up". Row opens `BudgetPanel` for edit users, else is not interactive. Footer hint (14/400 muted): "Budgets carry over to next month until you change them." Empty: `UiEmptyState` "No budgets yet" / "Set a monthly limit for a category to see progress here." action "Add budget" (edit users; view-only gets title and body only).
- Charts: see Charts section. Charts card pair stacks below 800px content width, side by side from 800px.
- Empty month (no transactions and accounts exist): cards show exact zero amounts, charts show their empty line ("No spending recorded this month." / "Not enough data yet."), no extra empty state.
- First use, admin, no accounts: `UiEmptyState` "Add your first account" / "Accounts hold your transactions. Start with the one you use most." primary "Add account" (opens `/finance/accounts?acct=new`). Non-admin with no visible accounts: `UiEmptyState` "No accounts to show" / "Ask an admin to share an account with you.", no action. Toolbar, tabs and "Add transaction" are not rendered for any viewer with zero visible accounts.

### 2. Transactions (`/finance/transactions`)

Focal point: the first transaction row of the month (newest first) with its amount at the end edge, because scanning recent money in and out is the job of this tab.

- `TransactionFilters`: search `UiInput` "Search transactions" (matches description, debounced 300ms, server-side), and a "Filters" disclosure button (`aria-expanded`, shows "Filters ({n})" when active) revealing `UiSelect`s Type (All, Income, Expense, Transfer), Category (All categories + family list + Uncategorized), Source (All, Entered by hand, Imported). On container width >= 640px the filters are always visible inline; below they collapse into the disclosure. Active filters also appear as removable `UiChip`s (`X` button, `aria-label` "Remove filter {name}") and a ghost "Clear filters". The account filter is the shared chip row (not duplicated). Date range is the month switcher.
- List: ordered by date descending, then entry time; grouped under day sub-headings (`<h3>`, Label 14/600 muted, `Intl` weekday + date) so the date column is not repeated. Server-paged 50 at a time; secondary button "Show more transactions" at the end (no infinite scroll); count line "{n} transactions" (`aria-live="polite"`).
- `TransactionRow` at content width >= 640px renders as a `UiTable` row with columns Description (Body 400 plus Imported tag and "Matches {name}" meta), Category, Account (hidden when one account is selected), Amount (end edge). Below 640px (including 320px) it renders as a two-line stacked row, no horizontal scroll: line 1 = kind icon, description (wraps up to 2 lines, then ellipsis), amount at the end edge (16/600, never wraps, description yields); line 2 = muted 14/400 meta: category, account, Imported tag, wrapping freely. The row is one `<button>` (min 56px, `aria-label` = "{description}, {kind}, {amount}, {date}") opening `TransactionPanel`. `UiTable` sticky header applies only to the wide layout.
- Transfers: when both accounts are visible the row shows `ArrowLeftRight` and "Transfer from {from} to {to}"; amount unsigned (no "+" or minus), in the viewed account's currency. A transfer with a hidden counterpart renders as an ordinary income or expense row (see Privacy), with no special wording or icon.
- States: loading = 8 `UiSkeleton` rows. Empty (no transactions in month, no filters): `UiEmptyState` "No transactions this month" / "Add a transaction or import a bank statement." with primary "Add transaction" and secondary "Import CSV". Empty with filters: "No transactions match these filters" / "Try different filters." action "Clear filters". Error: `UiErrorState` with "Try again". Load-more failure: danger `UiAlert` above the button "We could not load more transactions. Try again." with the button retained.

### 3. Transaction panel (`TransactionPanel`)

Focal point: the Amount field, with kind chips above it, because amount and kind are what every entry needs; the rest is optional enrichment.

Presentation per 01.1/03/04: docked 360px at content width >= 900px, overlay on iPad, bottom sheet (max 85%) on phone, sticky footer, Esc closes, focus to Amount on open (create) or panel heading (edit), focus returns to opener. Panel h2 "New transaction" or "Transaction details". View-only users get the same layout as read-only text (no inputs, only "Close").

Field order (single column, 16px gap):
1. Type: radiogroup of 3 `UiChip`s "Expense" (default) / "Income" / "Transfer", arrow-key roving, exactly one on. Changing kind to/from Transfer keeps amount and date, clears category. A transfer with a hidden counterpart is delivered as an ordinary income or expense; the panel has no special case for it.
2. Amount (`UiInput`, required) with read-only currency suffix from the chosen account.
3. Date (`type=date`, default today in family time zone, required).
4. Description (`UiInput`, max 160; placeholder none). Required for expense and income.
5. Category (`UiSelect`, expense/income only; groups by kind; default Uncategorized). Hidden for Transfer.
6. Account (`UiSelect`, visible and writable accounts only, default = selected chip or the first). For Transfer: "From account" and "To account" selects instead; selecting the same account or different currencies shows inline errors and disables save.
7. Note (`UiTextarea`, 3 rows, max 1000, optional).
8. Edit mode, read-only info rows (Label 14/600 + value): "Imported" tag with import date when applicable; and when matched to a recurring expense, the line "Counts as payment for {name}, due {date}." with ghost "Unmatch payment" (`Unlink2`, no confirm, toast).

Footer: primary "Save transaction", secondary "Close" (dirty form opens "Discard changes?"). Edit adds danger ghost "Delete transaction" (`Trash2`, start edge) with confirm (default focus "Keep transaction").

Behavior: single save path, save enabled when dirty and valid; success toast "Transaction saved", create closes panel, edit stays open. After save, the server re-runs expected-vs-actual matching and the lists reload; if a new transaction auto-matches an occurrence the toast stays the same and the row shows "Matches {name}". Validation inline, focus to first invalid. Server error: danger `UiAlert` at panel top "We could not save the transaction. Nothing was changed. Try again." Selections kept.

### 4. Recurring tab (`/finance/recurring`)

Focal point: in Calendar mode the first day cell with an Overdue or the next Upcoming payment (overdue marked with icon and count), in List mode the first row of the Overdue group, since "what is late or next" is this tab's single question.

Order: `StillToPayCard` (same as Overview), view switch (`UiChip` radiogroup "Calendar" default / "List", `role="radiogroup"`, label "View"), primary-adjacent secondary "Add recurring expense" (edit users; phone: full-width 44px button under the switch), then content. View choice is remembered in `localStorage` key `fh-finance-recurring-view`.

## Interaction and Accessibility Contract (additions to 01.1 to 04)

- Semantics: tabs are route-backed `UiTabs`; account and view choices are `role="group"`/`radiogroup` of toggles with `aria-pressed`/`aria-checked`; transaction list is a `<ul>` of `<li><button>` on phone and a `<table>` on wide screens (one markup per breakpoint, switched by container query, never both in the DOM); calendar is a `<table>` with `<th scope="col">`; budgets and chart rows are `<ul>`; stepper is `<ol>`; panels are `<aside aria-label="Transaction details">` (or "New transaction", "Payment details", and so on).
- Live regions: toasts `role="status"`; month label `aria-live="polite"`; results count `aria-live="polite"`; import done `role="status"`; panel and commit errors `role="alert"`; calendar and charts have no live region.
- Keyboard: Tab order is one stop per row, per account chip group (arrow keys inside), per calendar (roving, arrow keys move by day and week); Esc closes panel and dialogs; Enter in text fields does not submit multi-field forms; filters disclosure is a button; import review checkboxes are independent Tab stops.
- Never colour alone: statuses and budget states are tag text plus icon; amounts carry U+2212 or "+" and kind icon; charts carry text values and a table alternative; selected day and selected chip use fill plus border/weight.
- Touch: 44px hit areas for all controls (calendar width exception documented in Spacing).
- 320px and 200% zoom: no horizontal scroll anywhere; tables are `UiTable` responsive (label/value stacking) except `TransactionRow` and import review rows, which use the specified stacked two- or three-line layout; the calendar stays 7 columns (cell text hidden below 560px, count chip plus icon only); chart rows and balance chart reflow to container width; toolbar wraps; amount never wraps, text yields.
- Dates: `Intl.DateTimeFormat` in the active locale and family time zone, `<time datetime>`; due status (Overdue vs Upcoming) and expected-vs-actual are computed server-side and displayed only; the UI never computes occurrences, matches, sums, budget percentages or over-budget amounts (all come from the server).
- User content (descriptions, payee hints, account names, category names, recurring names, imported text) rendered as text only, never HTML, including in toasts, `aria-label`s and chart text. CSV cells beginning with `=`, `+`, `-`, `@` are displayed as text; export is out of scope.
- Long text: descriptions clamp to 2 lines on rows, full text in the panel; tags and buttons may wrap to 2 lines (01.1). Pseudo-long (+40%) test covers rows, status tags, budget rows, calendar aria labels, review rows and import buttons in SK/PL.
- Dark mode: all marks and tags use tokens; verify chart marks, track, dashed zero line and struck-through rows in both themes.
- Tests: Vitest + axe on Overview (per currency, empty, loading, error, over-budget), Transactions (wide, 320px, filters open, empty, filtered empty), panels (transaction in each kind, read-only, bill panel in each status, recurring, account with visibility chooser, category delete, budget), calendar (month with overdue), charts (chart and table modes), import (each step, duplicate and unreadable rows), each in light and dark and en/sk/pl; contrast assertions for chart marks; the privacy differential tests above; Pest 403 deep links; test that `MoneyAmount` formats from integer minor units without `Number` (property tests incl. amounts above 2^53 and zero-decimal currency fallback).

### Plurals: ICU-free pipe plurals (vue-i18n)

Do NOT use ICU `{n, plural, ...}` syntax in this phase. Use vue-i18n pipe plurals with the existing `pluralRules` in `resources/js/i18n.js` (order from `Intl.PluralRules`): **en has 2 segments** (`one | other`), **sk and pl have 4 segments** (`one | few | many | other`; sk `many` and pl `other` are fractional forms and are normally copied from `few`). Call `t(key, { n }, n)` so `{n}` renders the count. A one-form key still has all segments (never 3). Money strings are never pluralised.
