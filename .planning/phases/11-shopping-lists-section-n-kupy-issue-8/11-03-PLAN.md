## Decisions applied (orchestrator and UI-SPEC win over research)

- Delete list (UI-SPEC): only while open, by the creator or the effective responsible person. Archived lists cannot be deleted (UI-SPEC archived overflow has only Copy and Send by e-mail; overrides research D1 "creator can delete").
- List settings (UI-SPEC screen 5): while open, creator or effective responsible may change name, store, responsible person, contributors, viewers and reminder. While locked, only the effective responsible may change the responsible person and the reminder. Done: nothing.
- Copy (orchestrator + UI-SPEC screen 7, overrides research D5): copier becomes creator; `keep = true` keeps store, the effective responsible person, contributors and viewers, and adds the original creator (if not the copier or the responsible) as contributor when they hold Shopping edit, else as viewer; `keep = false` keeps the store, makes the copier responsible and adds no members. Items copied unmarked (state pending) with name, quantity, unit, note, catalog link, position; no reminder; status open; `source_kind = copy`. Allowed from any status for anyone who can view the list and holds Shopping edit.
- Carry-over (research D6, D7; UI-SPEC screen 6): new open list with the original creator, the effective responsible, the same store and the same contributors and viewers, only the unavailable items (reset to pending, quantities and units kept), no reminder, `source_kind = carry`, name passed in by the caller (the UI builds "{name} (unbought)" in the user's locale and the seed passes its own), max 80 characters.
- E-mail ability (orchestrator, overrides UI-SPEC "viewers included"): creator, effective responsible and contributors with Shopping edit, in every list status; never viewers.
- D9 lock of an empty list refused; D10 unlock keeps marks; D1 done lists are read-only.
- Member pickers (UI-SPEC screen 5): responsible must `canSignIn()` and hold Shopping edit; contributors need Shopping edit; viewers need Shopping view or edit; children (Phase 10) may be chosen as contributors or viewers. A person holds at most one role; the creator and the responsible person are never stored as members.
- A member whose module level is only `view` acts as a viewer everywhere, whatever role they were given.

## Contracts

- `ResponsiblePerson::eligible(User $u): bool` = `$u->canSignIn()` and AccessGate level for Shopping is Edit. `effective(ShoppingList $l): User` = responsible row if it exists and is eligible, else the creator. `isFallback(ShoppingList $l): bool` and `previousName(ShoppingList $l): ?string` (name of the ineligible responsible when the row still exists, else null).
- `ShoppingAccess` (constructor: AccessGate, ResponsiblePerson; no admin bypass): `role(User, ShoppingList): ?string` in creator|responsible|contributor|viewer (effective responsible wins over creator when they differ), `canView`, `canEditSettings`, `canChangeResponsible`, `canSetReminder`, `canManageMembers`, `canEditItems`, `canLock`, `canUnlock`, `canMark`, `canFinish`, `canCopy`, `canMail`, `canDelete`, and `abilities(User, ShoppingList): array<string,bool>` with keys editSettings, changeResponsible, setReminder, manageMembers, editItems, lock, unlock, mark, finish, copy, mail, delete, manageCatalog (= Shopping edit). Every can* first requires the module level (view for canView, edit for everything else).
- `ListQuery::visibleTo(User $u): Builder` = lists where creator_id = u or responsible_id = u or a member row for u exists. Uniform 404 for everything else is the caller's job (`visibleTo(...)->findOrFail`).
- `ListMembers::sync(ShoppingList $locked, array $contributorIds, array $viewerIds): void` with eligibility per Decisions, 422 (`ValidationException` key `contributors` / `viewers`, message `shopping.error.member_not_eligible` or `shopping.error.member_overlap`) on a forged or overlapping id. Called only with the list row already locked.
- `ListService`: `create(User $actor, string $name, ?int $storeId, ?int $responsibleId): ShoppingList` (actor needs Shopping edit; responsible defaults to actor; must be eligible), `updateSettings(User $actor, int $listId, array $data): ShoppingList` (keys name, store_id, responsible_id, contributor_ids, viewer_ids, remind_at as a UTC CarbonImmutable or null; per-field permission per Decisions; changing remind_at resets reminder_enqueued_at to null), `delete(User $actor, int $listId): void`.
- `ItemService`: `add(User $actor, int $listId, array $items): array{added: int, merged: list<string>}` (each item has catalog_item_id or name, quantity as a normalised string, unit_id, note, save_to_catalog; a catalog item already on the list as a pending row with the same unit increases that row's quantity, capped at 999.99, and its name is reported in `merged`; a free-text item with save_to_catalog creates a catalog row with NameKey or links to the existing one with the same name_key; positions append), `update(User $actor, int $listId, int $itemId, array $data)`, `remove(User $actor, int $listId, int $itemId)`. All require status open and canEditItems.
- `ListStateService`: `setLocked(User $actor, int $listId, bool $locked): ShoppingList` (absolute and idempotent; lock needs at least one item else 422 `shopping.error.lock_empty`; done -> 409), `setItemState(User $actor, int $listId, int $itemId, ItemState $state)` (absolute; list must be locked else 409; records state_changed_at/by), `finish(User $actor, int $listId, ?string $carryName): array{list: ShoppingList, carry: ?ShoppingList}` (locked and no pending item else 409; writes done_at, done_by, store_name snapshot; carry only when carryName is given and an unavailable item exists; a replay on a done list returns the existing carry list and changes nothing), `copy(User $actor, int $listId, string $name, bool $keep): ShoppingList`.
- Every mutation runs in `DB::transaction` and starts with `ShoppingList::query()->whereKey($id)->lockForUpdate()->firstOrFail()` after the visibility check (hidden -> 404, visible but not allowed -> 403), then re-checks the status under the lock (research Pattern 2).
