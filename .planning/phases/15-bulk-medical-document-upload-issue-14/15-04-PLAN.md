<objective>
The member side of upload batches: everything a member can do with a batch, scoped through the existing Visibility layer (D-06), persisting every choice server-side (D-02), with Continue implemented on top of the Phase 8 accept/reject path (D-03, D-07) and re-scan feeding the 15-03 tick with the 15-02 adjustments (D-04).

Decisions (Claude's discretion, recorded):
- Access: Health Edit on the person (Visibility at AccessLevel::Edit), the same level the AI review page needs. View-only members do not see batches (stricter than "may see", satisfies BULK-08's "limited to").
- Choices are stored as `{entryKey: {"decision": "approve"|"reject", "values": {field: string}|absent}}`; keys must exist in the item's ready proposal (ProposalEntries::isKey plus payload lookup); values only for the entry type's allowed fields, each at most `medical.upload_batches.max_choice_value_chars`. The full rule validation happens at Continue through AiReviewQuery::accept, whose ValidationException aborts the whole Continue (nothing saved) and returns the entry key with the messages.
- Continue with undecided findings leaves them undecided; they stay reviewable on the document's ordinary review page. Continue on a failed or never-read document keeps the document without findings. Continue is refused while the document's run is queued, running or waiting.
- Re-scan after a ready proposal supersedes it (existing finishReady), so stored choices are cleared at request time.
- Duplicates: the same file (sha256) twice in one batch is refused as `duplicate`; a file already stored as an ordinary document of the person is accepted and the item carries `duplicate_of` so the UI can say so.
- Unreadable or unsupported files are refused by the existing MedicalDocumentStore::put rules at upload (nothing stored, the uploader shows the reason); a document the AI cannot read ends as a failed item with Try again, Keep without findings and Remove.

Purpose: BULK-04, the request half of BULK-05 and BULK-06, the persistence of BULK-07 and the access rules of BULK-08.
Output: UploadBatchQuery, ItemState, an optional batch parameter on DocumentQuery::create, two Pest test files.

## Interfaces this plan provides (consumed by 15-05)

Every method takes `Viewer $viewer, MedicalSubject $subject` first and returns null for anything outside the Edit scope.
- `create(..., User $user, bool $acknowledged, ?array $shownProviders, bool $textNotice): array{result: 'created'|'exists'|'consent_off'|'unavailable'|'notice_required'|'denied', batchId?: string, providers?: list<string>}`
- `addDocument(..., string $batchId, array $stored, string $title, User $user): ?array{itemId: string, documentId: string, duplicateOf: ?string}` throws DocumentRejected('batch_full'|'duplicate'|'batch_closed'|'limit_reached')
- `page(..., string $batchId): ?array` (Inertia props, see Task 1) and `status(..., string $batchId): ?array` (polling payload)
- `setCurrent(..., $batchId, $itemId): ?bool`, `saveChoices(..., $batchId, $itemId, array $choices): ?array`, `saveAdjustments(..., $batchId, $itemId, array $values): ?array`
- `requestRescan(..., $batchId, $itemId, User $user, bool $acknowledged, ?array $shownProviders, bool $textNotice): ?array{result: 'queued'|'limit'|'done'|'consent_off'|'notice_required', providers?: list<string>}`
- `continue(..., $batchId, $itemId, User $user): ?array{result: 'continued'|'not_ready'|'finished', nextItemId: ?string, approved: int, rejected: int}` throws ValidationException keyed `entries.<entryKey>.<field>`
- `removeItem(..., $batchId, $itemId, User $user): ?bool`, `delete(..., $batchId, User $user): ?int`
After any write that can start AI work (create returns nothing to kick; addDocument, requestRescan, continue, removeItem), the controller calls `BatchKicker::kick($batchId)` after commit.
