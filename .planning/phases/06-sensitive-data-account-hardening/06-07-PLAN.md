## Phase Goal

**As a** family member with access to Health or Finances, **I want to** protect my account with an authenticator app or passkey and be asked to confirm it's me after inactivity, **so that** medical and money data stay private even when a password leaks or a device is left unlocked.

<objective>
Deliver the admin side end to end: the "require two-step verification" switch with its enforcement proven through the sensitive gate, per-member factor status in the members panel, and the audited admin reset that revokes the member's sessions.

Purpose: CONTEXT "Admin can require a second factor for members who have health or finance access (setting, default off). Enforcement: members under the requirement without a factor are guided to set one up before opening sensitive modules." and "admin can reset a member's second factor (audited, that member's sessions revoked)"; UI-SPEC Screen 9 (as amended by A3: the switch needs the admin's security confirmation); research Pattern 7 (storage, who is under the requirement, guide-not-block, reset in a transaction); orchestrator decisions "app_settings table for the require-2FA toggle (guide-to-setup, not hard block)", "admin reset in a transaction (delete passkeys and 2FA columns, SessionRevoker::revokeAll, audit)". The gate's policy step itself shipped in 06-04 and the TOTP endpoints in 06-05; this plan adds the admin controls and proves the whole loop.
Output: 2 controllers, routes, matrix rows, members page additions (5 Vue files), 3 test files.

## Server contract (this plan)

- `PUT /settings/security/policy` name `settings.security.policy`, middleware `['access:admin', 'access:recent', 'throttle:20,1']` (revision Warning 1: turning the requirement off lowers protection for everyone, so both directions need the admin's 10-minute security confirmation; stale JSON caller -> 423 `{"error":"confirm_required"}`, nothing saved, no audit row; recorded as UI-SPEC amendment A3): body `{required: boolean}` (strict boolean validation); `SecondFactorPolicy::setRequired`; audit `SecurityPolicyChanged` meta {setting: 'require_second_factor', value: bool}; JSON caller 200 `{"required": bool}`; non-JSON 303 back with toast `members.security.on_toast` / `off_toast`.
- `DELETE /settings/members/{user}/second-factor` name `settings.members.second_factor.destroy`, middleware `['access:admin', 'access:recent', 'throttle:20,1']`, `whereNumber('user')`: the admin's own id -> 403; member without any factor -> 422 `{"error":"no_factor"}`; otherwise one DB transaction: null two_factor_secret/recovery_codes/confirmed_at, delete the member's passkeys rows with a query (no package action, so no per-passkey events), `SessionRevoker::revokeAll($member)`, audit `SecondFactorReset` (actor admin, target member, no meta). JSON 200 `{"reset":true}`; non-JSON 303 back with toast `members.security.reset_toast` {name}.
- MembersController adds per member `security` {totp: bool, passkeys: int, required: bool (policy required() && appliesTo(member)), needs: bool (mustEnrol(member))} and top-level props `securityPolicy` {required: bool, pending: int}, `confirmFresh` (admin's SensitiveSession::recentlyConfirmed()), `methods` = `App\Security\ReauthMethods::for(admin)` (06-04; same shape as /confirm-access). Passkey counts via a withCount-style single query; no two_factor_* or credential values.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| admin -> other members' factors | reset is an account-takeover vector |
| members page props -> admin browser | factor status of every member |
| admin session -> policy | requirement switch |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-06-36 | Elevation of privilege | admin reset from a hijacked idle admin session | mitigate | `access:admin` + `access:recent` (10-minute window), throttle, own-row refused |
| T-06-37 | Repudiation | resets and policy changes | mitigate | second_factor_reset (actor + target) and security_policy_changed rows |
| T-06-37b | Elevation of privilege | hijacked idle admin session switching the requirement off for everyone | mitigate | `access:recent` on settings.security.policy (both directions); stale test proves nothing saved and no audit row |
| T-06-38 | Spoofing | attacker keeps a session after reset | mitigate | SessionRevoker::revokeAll in the same transaction (session rows + remember token) |
| T-06-39 | Tampering | partial reset | mitigate | single DB transaction; failure test proves nothing changes |
| T-06-40 | Information disclosure | members props | mitigate | booleans and counts only; test scans for two_factor_ and credential_id |
| T-06-41 | Denial of service | requirement locking members out | accept | guide-not-block: only Health/Finances redirect to setup; the rest of the app stays usable (owner decision) |
