## Decisions fixed for this plan

- config/fortify.php: features `[Features::resetPasswords(), Features::twoFactorAuthentication(['confirm' => true, 'confirmPassword' => false, 'secret-length' => 32])]`; limiters `['login' => 'login', 'two-factor' => 'two-factor']` (limiter defined in 06-02). Never add `Features::passkeys()` (registers passwordless login, out of scope).
- FORTIFY_RULES additions: two-factor.login and two-factor.login.store -> ['guest']; two-factor.enable and two-factor.confirm -> ['recent'] (revision Blocker 1: enrolling a factor needs the 10-minute security confirmation; stale JSON callers get 423 `{"error":"confirm_required"}` from the 06-02 rule, nothing is stored); two-factor.disable, two-factor.qr-code, two-factor.secret-key -> ['authenticated'] (qr/secret are reachable only while a pending secret exists, which itself needed a recent enable; disable keeps its own conditional check below so "Cancel setup" of an unconfirmed secret never needs a confirmation); two-factor.regenerate-recovery-codes -> ['recent']; two-factor.recovery-codes (GET, returns plaintext codes at any time) -> ['disabled']; password.confirm, password.confirm.store, password.confirmation -> ['disabled'] (unknown rule = deny: guest 302, signed-in 403).
- GuardTwoFactorRoutes (web group, after ThrottleAuthRoutes; switch on route name):
  - `login` GET: forget login.id, login.remember, login.at ("Back to sign in" clears the pending login).
  - `two-factor.login`, `two-factor.login.store` and any name starting `two-factor.passkey.`: if login.id is set and (login.at missing or now - login.at > security.challenge_ttl_seconds): forget the three keys; JSON caller -> 410 `{"error":"challenge_expired"}`, otherwise redirect /login with status `challenge_expired`. For two-factor.login.store reject array-valued `code`/`recovery_code` with 422.
  - `two-factor.enable`: 409 `{"error":"already_enabled"}` when TOTP is confirmed (blocks `force` replacing a live secret). Recency is enforced by the route's `access:recent` rule, not here.
  - `two-factor.qr-code`, `two-factor.secret-key`: 404 unless a secret exists and two_factor_confirmed_at is null (secret visible only while pending).
  - `two-factor.confirm`: reject array `code` (422); per-user limit 5/min (key `tfa-confirm:<id>`) -> 429 JSON {error:'throttle', minutes}.
  - `two-factor.disable`: when TOTP is confirmed and `SensitiveSession::recentlyConfirmed()` is false -> 423 `{"error":"confirm_required"}`; unconfirmed (cancel setup) passes without confirmation; after the response, if it was confirmed and the status is < 400, audit `TwoFactorDisabled`.
  - `two-factor.regenerate-recovery-codes`: 404 unless TOTP is confirmed.
- Response bindings in FortifyServiceProvider::register (anonymous classes, same style as the existing ones):
  - LoginResponse: `SensitiveSession::confirm()`; JSON -> `{"two_factor":false}`; else redirect `SafeIntended::pull()` (303).
  - TwoFactorLoginResponse: `confirm()`; if the request had a recovery_code, flash toast `{key: 'twofactor.recovery.used', params: {n}, count: n}` with n = remaining codes; redirect `SafeIntended::pull()` (303).
  - FailedTwoFactorLoginResponse: JSON 422 / else redirect route two-factor.login with errors `recovery_code => twofactor.error.recovery` when a recovery code was sent, else `code => twofactor.error.code`.
  - TwoFactorEnabledResponse `{"enabled":true}`; TwoFactorConfirmedResponse and RecoveryCodesGeneratedResponse `{"recoveryCodes":[8 codes]}` with `Cache-Control: no-store, private`; TwoFactorDisabledResponse `{"disabled":true}`. Non-JSON callers get `back()` (no status constant strings, research Pitfall 7).
- Boot: `Fortify::redirectUserForTwoFactorAuthenticationUsing(RedirectIfSecondFactor::class)`; `Fortify::twoFactorChallengeView(...)` renders `Auth/TwoFactorChallenge` with props `{totp: bool, passkey: bool}` for the challenged user (User::find(session login.id)); passkey = security.passkeys_enabled && user has passkeys. No ids, names or emails.
- RedirectIfSecondFactor extends `Laravel\Fortify\Actions\RedirectIfTwoFactorAuthenticatable`: validateCredentials (keeps the dummy-hash timing path and Failed event), then if `hasSecondFactor()` put `login.at` = now and return `twoFactorChallengeResponse`; else `$next`.
- Sign-in opens the security window: LoginResponse / TwoFactorLoginResponse call `SensitiveSession::confirm()`, which sets `auth.password_confirmed_at`, so a member who just signed in can set up the authenticator app for 10 minutes without an extra prompt (legitimate flows keep working); after that the setup dialog's in-place ReauthForm (06-06) refreshes the window.
- AppShell flash toast: pass `toast.count` as the plural count when present (`t(key, params, count)`).
- Login.vue status map: `challenge_expired` -> info alert `twofactor.error.expired`.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| holder of a valid password -> second step | password alone must not sign in a member with a factor |
| signed-in session -> factor management endpoints | a hijacked session must not silently remove or read factors |
| Fortify defaults -> app contract | vendor routes become reachable when the feature is on |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-06-22 | Elevation of privilege | passkey-only members skipping the challenge | mitigate | RedirectIfSecondFactor checks hasSecondFactor(); test with a passkey-only user |
| T-06-23 | Spoofing | TOTP brute force at the challenge | mitigate | throttle:two-factor keyed by login.id (5/min + 10/15 min), session swap test, lockout audit, generic errors |
| T-06-24 | Spoofing | stale pending challenge reused later | mitigate | 10-minute login.at TTL, keys cleared on expiry and on GET /login |
| T-06-25 | Information disclosure | TOTP secret and recovery codes via Fortify GET routes | mitigate | qr/secret only while pending (404 after confirm), recovery-codes GET denied, codes returned once in no-store JSON |
| T-06-26 | Tampering | `force` re-enable replacing a live secret | mitigate | enable returns 409 when TOTP is confirmed |
| T-06-27 | Elevation of privilege | disabling a factor or regenerating codes from a hijacked idle session | mitigate | disable (when confirmed) and regenerate require the 10-minute recent window; audited |
| T-06-27b | Elevation of privilege | stolen or idle session enrolling its own authenticator, then passing the idle gate with it | mitigate | two-factor.enable and two-factor.confirm mapped to the `recent` rule (423 confirm_required when stale, nothing stored); sign-in sets the window; stale-session tests |

| T-06-29 | Elevation of privilege | stolen remember cookie opening finance | mitigate | confirmation only in LoginResponse/TwoFactorLoginResponse, never on the Login event; recaller test prompts |
| T-06-30 | Information disclosure | challenge page props | mitigate | only booleans {totp, passkey}; no ids or emails |
