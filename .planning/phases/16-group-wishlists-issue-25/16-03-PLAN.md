## Interfaces from 16-01

WishAccess::canEditWish(User, Wish), WishAccess::canEditGroup(User, int $groupId). GroupAccess::canView(User, WishlistGroup), isRecipientSide, canManage, isMember, members(WishlistGroup) -> list of {id, name}. ViewerContext::isRecipientSideOfWish(Wish). Wish relations group(), receivedBy(); columns group_id, received_by_id (forceFill only).

## Group list props shape (contract used by 16-04 and 16-06/07)

`ListPage::groupProps(WishlistGroup $group, User $viewer, Request $request)` returns `members` (the same WishlistMembers::forViewer list as today), `list` and `selected`. `list` = kind 'group'; owner {id: null, name: group name} (so existing components that read list.owner.name keep working); group {id, name, mode ('gifts'|'shared'), is_member, can_manage, members: [{id, name}]}; viewer_is_recipient = GroupAccess::isRecipientSide; viewer_is_manager false; can_edit = GroupAccess::canManage; wishes = active group wishes in the personal ordering (priority desc, created_at desc, id desc), presented; received (members only) ordered received_at desc, id desc. `selected` uses the same selected() validation (new only when can_edit; ids only from visible wishes). Page-level props `groups` and `group_candidates` are added by ListController in 16-04, not here.

WishPresenter: for group wishes only, the presented array gains `received_by` => {id, name} or null; personal wishes keep the exact current key set.
