## Planner decisions implemented here (record in the SUMMARY)

- **G-07 mode switch:** allowed after creation by any member with Wishlist Edit, only with `confirm_mode_change=true` (otherwise 422 with key `wishlist.group.error.confirm_mode`, nothing changes). The switch deletes every reservation (and so every contribution) on the list's wishes, in the same transaction that changes the mode, while the group row is locked. Reason: gifts to shared would otherwise reveal to members who reserved what (D-privacy); shared to gifts would leave members holding reservations on a list they are now recipients of. The response is the same whether or not reservations existed. The confirmation text in the UI (16-06) says that all reservations on the list are cancelled.
- **G-08 leaving and removal:** any member (Wishlist View is enough) can leave; the last member gets 409 and is told to delete the list. Members with Wishlist Edit replace the member set (the actor must stay in it, otherwise 422 `wishlist.group.error.self_required`; leaving is its own route). Added members must pass GroupAccess::isEligible and stay under `group_max_per_user` (422 `wishlist.group.error.member_not_eligible` / `wishlist.group.error.member_limit`; unknown ids give the same not-eligible error). Existing members who became ineligible may stay. Gifts mode: a newly added member's reservations and contributions on the list are deleted (they are recipient-side now). Shared mode: a removed or leaving member's reservations and contributions on the list are deleted (they lost access). A person removed from a gifts-mode list becomes an ordinary giver and from then on sees its reservations: accepted, identical to removing a wishlist manager today; the manual says so (16-08).
- **G-09 deleting:** any member with Wishlist Edit, after a confirmation in the UI; deletes every wish of the list (image files removed first through WishImageStore, links and reservations cascade), then the group (member rows cascade). Givers' reservations on it disappear from their shopping list. Not recoverable.
- **G-13 no step-up:** group routes do not require a recent password confirmation (unlike Settings > wishlist managers, which is an admin action). Membership grants access only to that one wish list among family members who already see the Wishlist module, the same level as shopping-list members. No audit entries (consistent with the rest of the Wishlist module, WishlistManagersTest "writes no audit entry").

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| browser -> /wishlist/groups* | group id, member ids, mode and flags are attacker-controlled |
| group member -> reservations of others | a mode switch or membership change must not reveal or keep reservations |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-16-06 | Elevation of privilege | IDOR on {group} in update/members/destroy/leave | mitigate | controller resolves the id, service re-checks canManage/isMember under lockForUpdate; unknown id and non-member both 403; matrix rows and tests |
| T-16-07 | Information disclosure | gifts -> shared switch revealing who reserved | mitigate | purgeGroup in the same transaction as the mode change, group row locked; confirmation required (G-07); identical response with and without reservations (test) |
| T-16-08 | Information disclosure | member added to a gifts list keeps their own reservation there (recipient-side holding giver data) | mitigate | purgeMember for added members in the same transaction; daily purgeAll |
| T-16-09 | Spoofing / abuse | invite abuse: adding arbitrary or ineligible users, or flooding someone with groups | mitigate | members must pass isEligible (sign-in + Wishlist Edit), max 12 members, max 10 groups per person, throttle 30-60/min per route |
