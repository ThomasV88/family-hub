# Phase 04 — UI Design Contract

> Visual and interaction contract for the Wishlist module: card gallery per member, wish form with multiple links, image states, giver detail panel with reservation and co-buy, occasions, giver reminder preferences. Generated by gsd-ui-researcher, verified by gsd-ui-checker.
> Sources: 04-CONTEXT.md (locked), 01.1-UI-SPEC.md (tokens and `Ui*` components, not redefined), 02-UI-SPEC.md (settings shell, confirm/discard patterns), 03-UI-SPEC.md (panel behaviour, notification preferences, toasts), sketch 005 winner D (shopping summary, person chips, occasion strip, own-list banner, card gallery). | `OccasionList`, `OccasionRow`, `OccasionPanel` | Occasions screen, rows, and the create/edit panel for custom occasions and member dates |
| `GiftReminderPrefs` | Section inside `/settings/notifications` |

## Color

Reuse 01.1 values. 60/30/10: dominant `--color-bg` (page), secondary `--color-surface` (cards, panel, summary) and `--color-surface-2` (image placeholder, selected card, hover), accent `--color-primary`, destructive `--color-danger`.

Accent reserved for (subset of the 01.1 closed list):
1. Primary button, one per view region: "Add wish" (topbar and empty state on own list), "Save wish" (panel), "Reserve gift" (reservation box when free), "Join co-buy" (co-buy form), "Save occasion", "Save dates"
2. FAB on phone ("Add wish", own list only)
3. Selected person chip, selected priority chip, checked checkbox/radio, switch ON
4. Focus ring, text links ("All occasions", "Open {name}'s list", link text in the wish links list)
5. Selected nav item "Wishlist"

Not accent: wish titles, prices, status tags, priority tags, occasion icons, the days-away tag, progress fill, image placeholders, the banner.

Semantic tags (always text plus icon, `UiTag` variants only):
- Available (others' lists only): `success` tag, text "Available"
- Reserved by name: `neutral` tag with `Gift`, "Reserved by {name}"
- Reserved by you: `neutral` tag with `Check`, "Reserved by you" (semibold)
- Co-buy: `neutral` tag with `Users`, "Co-buy, {people}"
- Priority: "Top wish" `neutral` tag with `Star`; "Would love" and "Nice to have" shown in the panel only (cards show a tag for Top wish only, to keep cards calm) (discretion)
- Days away: "Today" `warn`; 1 to 3 days `warn` with days text; otherwise `neutral`
- Received (own list archive): `success` tag with `Check`, "Received" (key `wishlist.received.tag`, deliberately outside `wishlist.status.*`)

Pledge progress (`UiProgress`): fill `--color-border-strong`, track `--color-surface-2`, always with text value; never accent, never danger.

Destructive (`--color-danger`) reserved for: "Delete wish" button and confirm, "Cancel reservation" confirm button when co-buyers exist, "Discard" in discard dialog, field errors, upload/load error text. The reservation conflict alert is `warning`, not danger.

## Screens and Interaction Contract

Routes (Inertia pages): `/wishlist` (gallery; panel via `?wish=`), `/wishlist/occasions`, `/settings/notifications` (new "Gift reminders" card). Home gets an "Upcoming occasions" card. Nav entry "Wishlist" (`Gift`) in `modules.js`. All routes `no-store`; wish images are served by an authenticated route with `Cache-Control: private, no-store`; nothing from these screens enters the service worker.

### Privacy contract (applies to every screen)

The recipient view must be indistinguishable from a list that has no reservation feature at all.

- **Recipient-equivalent definition.** `viewer_is_recipient` is true for a list if and only if the viewer is (a) that list's owner, or (b) the designated manager of that specific list (a per-list manager relationship, for example a parent for a child). A general wishlist `edit` grant (carried by the Parent and Child presets) means only: may reserve and co-buy on other people's lists like any giver, and may edit their own list and lists they manage. Admin role does not make anyone a manager or recipient-equivalent; an admin is a giver on every list they do not own or manage unless designated manager. The manager designation is configured by the admin per list (storage is decided by the planner; the UI only consumes the server flag).

| Viewer relation to the viewed list | View | Reservation UI | Add/edit wishes |
|---|---|---|---|
| Owner | `OwnListView` | none | yes |
| Designated manager of that list | `OwnListView` with banner "You are managing {name}'s list." | none | yes, label "Add wish for {name}" |
| Anyone else with view access (including holders of a general edit grant and admins who are not the list's manager) | `GiftListView` | yes, reserve and co-buy | no (no add tile, FAB or topbar button) |

- On `OwnListView` (viewer is recipient-equivalent for the viewed list: owner or designated manager of that list only): no status tags, no reservation or co-buy words in any visible text, `aria-label`, `title`, tooltip, empty-state text, toast, live-region text, dialog or banner; no counts of reserved, available or contributed items; no "reserved" filter or sort; no skeleton, spacer or reserved space for a status row; wish cards are the same height whether or not the wish is reserved; no polling of reservation state; no Inertia prop, `data-*` attribute or hidden DOM node carrying reservation data about the viewed list's wishes. `OwnListView` never renders `ShoppingSummary` and its page props never include the `shopping` prop. Layout must not shift when a giver reserves.
- The owner can mark a wish "Received" and delete it. Neither action shows or asks anything about reservations. Delete confirm copy is the same whether or not the wish is reserved. The Received group renders with the same neutral `wishlist.received.tag` whether or not the wish was reserved.
- Edit panels (`OwnWishPanel`, including "New wish for {name}") never contain a reservation box, for owners and designated managers alike (everyone else sees `GiftListView`, which has no edit panel).
- A designated manager (set by the admin per list, for example a parent for a child) managing a child's list sees `OwnListView` for that child with banner "You are managing {name}'s list." Their own reservations on other members' lists are visible only on `GiftListView` pages and in `/wishlist/occasions` through `ShoppingSummary`. Reservations they hold on the child's list are excluded server-side (see `ShoppingSummary`) and never rendered.
- `ShoppingSummary` and giver reminders contain only the viewer's own reservations on lists where the viewer is a giver (not recipient-equivalent).
- Search, exports and notifications: no reservation text. Giver reminders: see Reminders.
- Tests (Vitest + axe, plus Pest leak tests): snapshot `OwnListView` and `OwnWishPanel` DOM with a reserved wish versus an unreserved wish and assert equality, covering the Received group and the managed-child state (designated manager); also assert a viewer with a general edit grant and an admin who is not the list's manager both get `GiftListView` with the reservation box and the `shopping` prop for that list; assert the `OwnListView` Inertia props are identical for reserved and unreserved states and contain no `shopping` prop (Pest, also with a viewer who holds reservations elsewhere, and with a viewer who became manager of a list they had reserved on); assert that neither `wishlist.status.*` nor `wishlist.res.*` keys appear in the rendered text of any own-list state in en/sk/pl (a wholesale ban, which is why Received uses `wishlist.received.tag`).


### 1. Wishlist gallery (`/wishlist`)

Focal point on own list: the first wish card with the "Add wish" tile directly before it; on someone else's list: the first card with an "Available" tag, so the next gift to buy is the first thing seen.

Region order from top (sketch 005, 16px gap):
1. Page header: h1 "Wishlist". At container width >= 640px the topbar shows primary "Add wish" only while the own list is selected; phone uses the FAB (own list only). Never shown on other members' lists unless the viewer is the designated manager of that list (then label "Add wish for {name}"). A designated manager of another member's list gets `OwnListView` for that list (banner "You are managing {name}'s list.", no giver controls, no status tags, no reservation box); the edit panel is `OwnWishPanel` with no reservation box. They are recipient-equivalent for that list and cannot reserve on it. A viewer who merely holds a general edit grant or admin role (not the manager of that list) gets `GiftListView` with no add control and can reserve like any giver.
2. `ShoppingSummary` (`GiftListView` only, when applicable, collapsed by default; absent on `OwnListView`).
3. `PersonChips`.
4. `OccasionStrip`.
5. List banner (own list: neutral `UiAlert` info, text "This is your wishlist. Everyone with access can see it." Dismissible per session. Managed child list: "You are managing {name}'s list." Another member's list: no banner, instead a list header line: avatar, "{name}'s wishlist" (Heading), muted "{n} wishes".)
6. Gallery.

Gallery (container query on `.content`, `grid-template-columns: repeat(n, minmax(0, 1fr))` with no minimum tile width, gap 16px): 1 column below 340px content width (320px viewport, 200% zoom), 2 columns by default (phone), 3 from content width 560px, 4 from 800px. With the docked panel open the container query naturally reduces columns. Order on own list: by priority (Top wish, Would love, Nice to have), then newest first. On others' lists: Available wishes first, then reserved/co-buy, each by priority then newest (discretion: puts actionable gifts first; this ordering only exists in `GiftListView`, the owner order never depends on reservations). Received wishes leave the gallery and live in a collapsible "Received ({n})" group (own list only, `aria-expanded`, `Archive` icon), read-only cards without a panel action except "Delete wish".

`OwnWishCard` anatomy (radius 12px, 1px `--color-border`, `--color-surface`, no shadow): `WishImage` 4:3 on top (radius 12px 12px 0 0), body padding 12px: title 16/600 (2 lines clamp), price 14/600 ("{amount}" via `Intl.NumberFormat` currency, omitted when no price), meta line 14/400 muted: `Link` icon with "{n} links" (only when >= 1) and the Top wish tag. Whole card is one `<button>` that opens `OwnWishPanel` (`aria-label` = title). No other controls on the card.

`GiftWishCard`: same plus a status tag line at the bottom (always one tag line, so all cards on a giver list have equal height). Selected card (panel open): `--color-surface-2` fill plus 2px border `--color-border-strong`, no accent.

Own list "Add wish" tile: first grid cell, dashed 1px `--color-border-strong` border, `Plus` icon and text "Add wish", same height as a card, opens create panel. Hidden for view-only users.

Cards of a reserved-by-viewer wish on a giver list carry the "Reserved by you" tag and nothing else changes.

States:
- Loading: 6 `UiSkeleton` cards (image block, two text lines).
- Empty own list: `UiEmptyState` "Your wishlist is empty", body "Add things you would like to get, with a link or a photo.", action primary "Add wish".
- Empty other list: `UiEmptyState` "{name} has not added any wishes yet" with body "Check back later.", no action.
- Empty received group: group is not rendered.
- Error: `UiErrorState` "Something went wrong" / load body, action "Try again". Module access none = 403 `UiErrorState` (Phase 2). `?wish=` for an id the viewer cannot see or that does not exist renders the same 403 state (no existence leak).
- Viewers who are neither owner nor designated manager of the list (including general edit-grant holders): no add tile, no FAB, no topbar button; they can still reserve on others' lists if they have view access (reserving is a giver action available to anyone with view access except the recipient and recipient-equivalents).

### 2. Wish form, owner panel (`OwnWishPanel`)

Focal point: the Title field at the top with "Save wish" pinned at the bottom, so a wish needs two actions and the rest is optional.

Presentation per 01.1/03: docked 360px at content width >= 900px, overlay on iPad, bottom sheet (max 85%) on phone, sticky footer, Esc closes, focus to Title on open (create) or panel heading (edit), focus returns to the opener on close. Panel h2: "New wish" in create mode, "Wish details" in edit mode.

Field order (single column, 16px gap):
1. Title (`UiInput`, required, max 120).
2. Image block (`WishImage` large 4:3 plus buttons): "Upload image" (secondary, leading `ImagePlus`, file input `accept="image/jpeg,image/png,image/webp"`, max 5 MB, discretion) and, only when at least one link exists, "Load image from link" (secondary, `RefreshCw`). Remove: ghost "Remove image" when an image exists. See Image states.
3. Links (`LinksEditor`): label "Links". Each row: URL `UiInput` (`type="url"`, `inputmode="url"`, placeholder "https://") and Label `UiInput` (optional, placeholder "Shop or note, optional"), remove icon button (`X`, `aria-label` "Remove link {n}"). Secondary "Add link" (leading `Plus`) below; up to 5, then button disabled with hint "You can add up to 5 links." Empty rows are ignored on save. Only http/https accepted; inline error on blur. The first valid link is the source for automatic image loading.
4. Price: amount `UiInput` (`inputmode="decimal"`, accepts locale comma or dot) and Currency `UiSelect` (EUR default, PLN, CZK, USD, GBP). Hint "Optional. A rough price helps others plan." Side by side at panel width 360px (amount flex, currency 112px) and stacked below 340px.
5. Size or variant (`UiInput`, label "Size or variant", placeholder "For example size M, blue").
6. Priority: radiogroup of 3 `UiChip`s "Top wish" / "Would love" / "Nice to have", exactly one on, default "Would love", arrow keys move between them.
7. Notes (`UiTextarea`, 4 rows growing to 12).

Footer: primary "Save wish", secondary "Close" (`wishlist.close`; when the form is dirty it opens the "Discard changes?" dialog, so no button is labelled "Cancel" next to "Discard"). Edit mode adds secondary "Mark as received" (leading `Check`, confirm-free, toast "Wish marked as received", moves it to Received) and danger ghost "Delete wish" (`Trash2`, at the start edge). Delete confirm dialog (default focus "Keep wish"): body "Delete "{title}"? This cannot be undone." Same body whether or not anyone interacted with the wish.

Behavior:
- Single save path (as 03): save enabled when dirty and valid. Success: toast "Wish saved"; create mode closes the panel; edit mode stays open. If a link was added or changed and no image exists, the server queues image loading and the card shows the image-loading state.
- Validation inline per field, focus to first invalid: title required, URLs valid http(s), price a non-negative number with up to 2 decimals, notes max 2000.
- Unsaved changes: `UiConfirmDialog` "Discard changes?" (Discard danger, "Keep editing" secondary default focus), copy from 03 under `wishlist.discard.*`.
- Server error: danger `UiAlert` at panel top "We could not save the wish. Nothing was changed. Try again." Selections kept.
- Designated managers acting on a child's list see "New wish for {name}" as the panel h2 (create mode).

### 3. Image states (`WishImage`)

One component, four visual states, announced through a `role="status"` live region inside the panel only (cards stay silent):
- Loading (job pending after save, or "Load image from link" pressed): `UiSkeleton` block in 4:3, centred `Gift` icon at 50% opacity is NOT used (skeleton only); panel text "Looking for an image on the link..." (14/400 muted). Client refreshes the wish with an Inertia partial reload every 3 seconds up to 10 times (30 s), pausing when the tab is hidden (discretion); after that the state becomes None with the hint below. Owner and giver views both poll image state only, never reservation state.
- Found: `<img>` with `object-fit: cover`, `alt=""` (title is adjacent text), `loading="lazy"`, `decoding="async"`, intrinsic ratio reserved to avoid layout shift, 1px inner border `--color-border`. Fetched image source label in panel (owner only), 14/400 muted: "Image from {host}."
- None (no link, job failed, no image on page): `--color-surface-2` block with `Gift` icon 32px in `--color-text-muted` (icon size exception for this placeholder). Never an error colour. In the owner panel: hint "No image found. Upload one to make this wish easier to spot." Failure details are not shown to the user.
- Upload: choosing a file shows the preview immediately with the Loading label "Uploading image..." and `UiProgress` indeterminate; success = Found. Errors (inline under the image block, danger text with `AlertCircle`): wrong type "Use a JPEG, PNG or WebP image.", too big "The image is larger than 5 MB.", failure "We could not upload the image. Try again." A manual upload always wins over an automatic image; "Remove image" then allows a re-fetch.

### 4. Giver detail panel and reservation (`GiftWishPanel`)

Focal point: the reservation box directly under the price, so what to do about this gift (reserve, cancel or join) is visible without scrolling.

Panel h2 "Wish details". Read-only content, top to bottom: `WishImage` 4:3, title (Heading), price (16/600) with size/variant line (14/400 muted "Size or variant: {value}"), priority tag, `ReservationBox`, Links list, Notes.
- Links: `UiList` rows, each an `<a target="_blank" rel="noopener noreferrer">` with `ExternalLink` icon, label (or host when no label) in accent link colour, host as 14/400 muted second line; visible text never the full URL. Accessible name "{label}, opens in a new tab".
- Notes: 16/400, rendered as text, `white-space: pre-wrap`.
- Footer: secondary "Close" only.

`ReservationBox` (`UiCard` inside the panel, padding 16px, heading "Reservation" 14/600, `aria-live="polite"` for state changes). States:

| State | Content | Actions |
|-------|---------|---------|
| Free | "Nobody is buying this yet." Hint "Your name will be visible to other family members, not to {name}." | primary "Reserve gift" |
| Reserved by you | "You are buying this." | secondary "Open for co-buying", ghost "Cancel reservation" |
| Reserved by you, co-buy open | "You are buying this. Co-buying is open." Contributors list (below), pledge progress | secondary "Close co-buying", ghost "Cancel reservation" |
| Reserved by another, no co-buy | "{name} is buying this." | none |
| Reserved by another, co-buy open | "{name} is buying this. Co-buying is open." Contributors list, pledge progress, viewer's own share if joined | primary "Join co-buy" (not joined) / secondary "Change my share" and ghost "Leave co-buy" (joined) |
| Co-buy closed | "{name} is buying this. Co-buying is closed." Contributors list | none (organizer sees "Open for co-buying" again) |

Contributors list (14/400, `<ul>`): row = `UiAvatar` 24px, name (organizer first with muted "(organizer)"), amount via `Intl.NumberFormat` or "no amount" muted. Pledge progress shown only when the wish has a price and at least one amount is set: "Pledged {sum} of {price}" with `UiProgress` (`role="progressbar"` values), over-pledge shows "Pledged {sum} of {price}" without error styling. Without price: "{people} in".

"Join co-buy" and "Change my share" open an inline form inside the box (not a dialog): `UiInput` "Your share (optional)" with currency suffix, hint "Leave empty if you will agree on amounts later.", primary "Join co-buy" / "Save my share" and secondary "Cancel". Amount must be a positive number with up to 2 decimals.

Behavior:
- Reserve and co-buy actions apply immediately (no panel-wide save), button `aria-busy`, toast: "Gift reserved", "Reservation cancelled", "Co-buying opened", "Co-buying closed", "You joined the co-buy", "Your share was saved", "You left the co-buy". After success the card tag updates through an Inertia reload of the list.
- Cancel reservation (no co-buyers): no confirm (reversible, as 03 skip). With co-buyers: confirm dialog "Cancel reservation" (see Copywriting), danger confirm "Cancel reservation", default focus "Keep reservation"; contributors are released.
- Leaving co-buy and closing co-buying: no confirm.
- Race: server returns conflict when someone reserved first; panel refreshes and shows a warning `UiAlert` "{name} just reserved this gift. Nothing was changed." (`role="alert"`).
- Server error: danger alert "We could not update the reservation. Nothing was changed. Try again."
- The organizer's reservation persists after the occasion passes until the owner marks the wish received (then the wish and its reservation leave giver lists); no auto-expiry UI.

### 5. Occasions (`/wishlist/occasions`)

Focal point: the "Upcoming" list's first row (the next occasion with its days-away tag), because "who is next" is the one question this screen answers.

- Page header: h1 "Occasions", primary "Add occasion" (topbar at >= 640px; on phone the primary sits at the end of the header row as a full-width-friendly 44px button; no FAB here).
- Section "Upcoming" (`UiList`, up to 12 months ahead, sorted by next date). `OccasionRow` (min 56px): leading type icon (`Cake`, `Sparkles`, `TreePine`, `CalendarHeart`, with `aria-label` of type), title "{name}'s birthday" / "{name}'s name day" / "Christmas" / custom title, second line 14/400 muted date via `Intl` (e.g. "Sat 7 Mar"), trailing days-away `UiTag` (`<time datetime>`), and link "Open {name}'s list" (opens `/wishlist?member={id}`; Christmas and custom family occasions link to the viewer's chip row, text "Open wishlists"). Rows for the viewer's own occasions show the same content, no reminder or reservation information.
- Section "Dates by member" (`UiTable` at >= 640px, stacked rows on phone): Member, Birth date, Name day (shows "Not set" muted). Row action "Edit dates" (visible to the member themselves and to admins) opens `OccasionPanel` in dates mode.
- Section "Custom occasions" (below upcoming): rows of custom occasions with "Edit occasion" for creator and admins.
- Occasion panel, dates mode: Birth date (`type=date`, max today), Name day calendar (`UiSelect` "Name day calendar": None, Slovak calendar, Polish calendar), conditional "Search a name" `UiInput` and a result `UiRadio` list "Name day" of matches ("{name}, {date}"; max 8; locale-collated, diacritics-insensitive match). Hint "Pick the name day that applies to {name}. You can change it later." Footer: primary "Save dates", secondary "Cancel".
- Occasion panel, custom mode: Title (`UiInput`, required), Date (`type=date`), switch "Repeat every year" (default on), For (`UiSelect`: "Whole family" or a member; default whole family). Footer: primary "Save occasion", secondary "Cancel", edit mode danger ghost "Delete occasion" with confirm (default focus "Keep occasion").
- Birthdays, name days and Christmas are generated and read-only (cannot be deleted); a member without a birth date shows no birthday row, and the dates table prompts "Add birth date".

## Interaction and Accessibility Contract (additions to 01.1, 02, 03)

- Semantics: gallery is a `<ul>` of `<li>`, each card one `<button>`; person chips are a labelled group of toggles with `aria-pressed`; list header is an `<h2>`; occasions list `<ul>`; panel is `<aside aria-label="Wish details">` (or "New wish").
- Live regions: toasts `role="status"`; reservation box `aria-live="polite"`; conflict and server errors `role="alert"`; image state `role="status"` in the panel only. No live region exists on `OwnListView` for reservation changes.
- Keyboard: Tab order on a card list is one stop per card; priority chips use arrow keys (roving radiogroup); Esc closes panel and dialogs; Enter in the Title field does not submit (multi-field form); the days-away checkboxes are independent Tab stops.
- Never colour alone: tags carry text and icon; progress carries numeric text; selected card has fill plus border.
- Touch: 44px hit areas for all new controls on phone and iPad.
- Money: `Intl.NumberFormat` with the wish currency in the active locale; amounts are decimal strings server-side, the UI never sums floats (sums come from the server).
- Dates: `Intl.DateTimeFormat` in the active locale and family time zone, `<time datetime>`; days-away is computed server-side in the family time zone and displayed only.
- External content: wish titles, notes, link labels and hosts are user content, rendered as text only, never as HTML, in toasts, `aria-label`s and push text. External image URLs are never hotlinked: the browser only loads images from the authenticated app route.
- Long text: titles clamp to 2 lines on cards, full title in panel; tags and buttons may wrap to 2 lines (01.1). Pseudo-long (+40%) test covers card status tag line, reservation box buttons, occasion rows and reminder checkboxes in SK/PL.
- Tests: Vitest + axe on gallery (own, giver, managed child, empty, loading, error), panels (own create and edit, giver in each reservation state), image states, occasions screen, reminder card, each in light and dark and en/sk/pl; the DOM-equality privacy test above; Pest feature tests cover 403 deep links.

### Plurals: ICU-free pipe plurals (vue-i18n)

Do NOT use ICU `{n, plural, ...}` syntax in this phase. Use vue-i18n pipe plurals with the existing `pluralRules` in `resources/js/i18n.js` (order from `Intl.PluralRules`): **en has 2 segments** (`one | other`), **sk and pl have 4 segments** (`one | few | many | other`; sk `many` and pl `other` are the fractional forms and are normally copied from `few`). Call `t(key, { n }, n)` so `{n}` renders the count. A one-form key still has all segments (never 3). Phase 3 keys written as ICU are outside this contract.
