## Decisions taken here

- Upload cap in the app is 5 MiB (UI-SPEC "The image is larger than 5 MB."), so PHP `upload_max_filesize=6M`, `post_max_size=8M`, nginx `client_max_body_size 8m` on the upload route only. The research numbers (8/9 MiB) are replaced by these to match the approved UI copy.
- The upload route URI (owned by plan 04-07) is `POST /wishlist/wishes/{wish}/image`; the nginx location regex is `^/wishlist/wishes/[0-9]+/image$`. Plan 04-07 adds the dev-stack smoke that proves a 2 MB multipart POST reaches PHP there (not 413, not 404) while the same body on another route gets 413.
- Backup of uploads streams a tar from a one-off app container (`docker compose run --rm --no-deps -T --entrypoint tar app ...`) into restic `--stdin`, the same no-plaintext pattern as pg_dump. It works when the app service is not running (local test) and on the server.
- Snapshot identity (fixes the "newest nightly snapshot is not the DB dump" problem):
  - Database snapshot: tags `<STACK_ENV>` and `<KIND>` exactly as today (unchanged, so every existing snapshot stays compatible), path `/<DB_NAME>.dump`.
  - Uploads snapshot: tags `<STACK_ENV>`, `uploads` and `uploads-<KIND>` (for example `uploads-nightly`), path `/uploads.tar`. It NEVER carries the bare kind tag (`nightly`, `manual`), so every existing `--tag nightly` / `--tag manual` selection keeps meaning "database". Every database selection additionally filters with `--path /<DB_NAME>.dump` as a second guard.
  - Uploads snapshots are taken for `nightly` and `manual` runs only. `pre-migrate` runs skip them (migrations never touch image files and deploys stay fast); backup.sh logs "uploads skipped (pre-migrate)".
  - Retention: database retention unchanged plus `--path /<DB_NAME>.dump`; uploads-nightly gets the same keep policy as the nightly database snapshots (`forget --tag uploads-nightly --path /uploads.tar` with the same KEEP array); uploads-manual, like manual database snapshots, is not pruned automatically.
  - Off-site copy copies the explicit snapshot ids of this run (database id, plus the uploads id when one was made), never `latest`.
  - Freshness: the database check uses `--tag nightly --path /<DB_NAME>.dump`; a second check requires an `uploads-nightly` snapshot not older than max_hours (missing counts as stale). The first uploads-nightly snapshot appears at the 03:45 nightly run after deploy, before the 09:00 freshness cron, so a normal daytime deploy does not alert.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| client -> nginx upload route | Untrusted request bodies up to 8 MB |
| app/worker -> uploads volume | Private image files written by the worker, served by the app |
| host -> restic repository (primary and copy) | Backup archives containing private images |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-04-04 | Denial of Service | nginx body limit | mitigate | 8m only on `^/wishlist/wishes/[0-9]+/image$`; every other route keeps the 1m default; PHP post_max_size 8M; app caps 5 MiB (plan 04-07); 413-vs-reach smoke in plan 04-07 |
| T-04-05 | Information Disclosure | uploads volume | mitigate | Mounted only in app/worker/scheduler under storage/app/private (outside public/); nginx never mounts it; local disk `serve => false` stays |
| T-04-06 | Information Disclosure | backups of images | mitigate | tar streamed straight into restic (encrypted, no plaintext file on disk); same password/copy policy as the DB dump |
| T-04-07 | Tampering | partial backup | mitigate | PIPESTATUS check; a failed tar or restic run forgets the partial uploads snapshot and exits non-zero (tested with UPLOADS_PATH) |
| T-04-07b | Denial of Service (recovery) | snapshot selection in drill, copy and freshness | mitigate | DB selected by `--path /<db>.dump`, uploads by distinct `uploads-<kind>` tags; copy uses explicit ids; local test proves both snapshots in the copy repo and a drill against it |
</threat_model>
