## Phase Goal

**As a** family member, **I want to** keep a gift wishlist that relatives can reserve from and chip in on, **so that** I get gifts I actually want while I never learn who is buying what.

<objective>
The privacy core: reservations and co-buying in separate tables behind a `Giving` namespace, the giver branch of the list page, the shopping summary endpoint, the manager purge, and the three leak tests (differential, canary, query-log) plus owner-action parity, written first in this plan before any giver UI exists.

Purpose: CONTEXT decisions "Any member except the recipient can mark 'I'm buying this'; visible with name to other givers, NEVER to the recipient in any view, count, badge, notification, export, search or API response", "A parent/manager who manages a child's list is treated like the recipient and never sees reservations on it", "A reserved gift can be opened for co-buying: other givers join with an optional amount; the organizer closes it", "Enforcement: reservation data in separate tables; owner/manager endpoints never select reservation columns; the endpoint matrix and dedicated leak tests prove no leak". Orchestrator decisions: giver = member with wishlist edit grant, view-only members see reservations read-only; purge job for reservations a manager made earlier; never audit reservations; never touch wishes.updated_at from reservation writes; never block owner delete/edit because reserved; no "bought" state and no admin cancel of reservations (research recommendations adopted; a departed member's reservations go with the user row through FK cascades).
Output: schema, models, Giving services, controllers, routes, matrix, privacy and feature tests.
</objective>

## Data model (research)

`wish_reservations`: id, wish_id FK wishes cascade UNIQUE, user_id FK users cascade (organizer), cobuy_state varchar default 'none' CHECK in (none, open, closed), timestamps. `wish_contributions`: id, reservation_id FK wish_reservations cascade, user_id FK users cascade, amount_minor bigint null CHECK > 0, timestamps, UNIQUE (reservation_id, user_id). The organizer always has a contribution row. No `touches`, no relation from Wish.
