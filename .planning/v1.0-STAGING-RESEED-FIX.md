# Staging reseed vs. audit: fix (2026-11-14)

## Root cause
Every staging deploy runs `staging:seed --force` and then `staging:audit`. The seeder deleted all `@example.test` users and recreated them with new ids. `audit_logs` and `ai_calls` are append-only (fh_app has no DELETE), so rows from testing (for example `login_failed`, actor = the old admin's id) survived with an id that no longer exists. The audit treated "id not in the synthetic users" as non-synthetic, so any audited action on staging blocked the next deploy (`3 non-synthetic audit_logs`). Domain rows created while testing had the same problem: `created_by` became NULL (FK set null) or dangled (tables without a FK), and the rules flagged them. Also found: `tasks.creator_id` and `wishes.owner_id` are RESTRICT, so the reseed itself would have crashed once a synthetic user had a task or wish.

## Semantics chosen
Seeder (`database/seeders/StagingSeeder.php`): in one transaction, before deleting the synthetic users, delete what they own, in FK-safe order: tasks (creator), wishes (owner) and ownerless/synthetic-owned occasions, finance matches/recurring/transactions/budgets/import profiles (created_by), import batches (user_id), accounts (created_by), AI extractions (started_by), medical subjects (created_by, only if unlinked or linked to a synthetic user). Cascades handle the children. Real users' rows are never matched. `audit_logs` and `ai_calls` are not touched. Medical files on disk are not deleted; `medical:prune-orphans` removes the files whose rows are gone.

Audit (`app/Console/Commands/StagingAudit.php`): a missing id can only be a deleted synthetic user, so rules test for a REAL thing:
- `audit_logs`: flagged on a non-synthetic meta email, OR actor_id/target_user_id of an existing non-synthetic user, OR a dangling id whose stored label is present and does not end in `(demo)`. Dangling id with a `(demo)` label or no label is accepted.
- `ai_calls`, `medical_ai_extractions`: flagged only when `started_by` is an existing non-synthetic user. Dangling is accepted.
- `created_by is null` stays flagged on the finance and medical rules. Decision: after the seeder change no synthetic-owned row survives a reseed (proved by the test "reseeds and audits cleanly after synthetic users created ... data", which asserts those tables are empty and the audit passes), so a NULL creator can only be a deleted real user, i.e. real data. Treating NULL as synthetic would hide that case.
- Known gap, accepted: a row created by a synthetic user but linked to a real person/user is kept by the seeder (conservative) and then flagged by the audit as null-created.

Existing test changed on purpose: `StagingAuditMedicalTest` "fails on an AI call whose starter no longer exists" encoded the old semantics; it is now "accepts an AI call whose starter no longer exists". The real-starter failure test next to it is unchanged.

## Test evidence (tests/Feature/StagingSeedTest.php)
Written first and run against the unfixed code: 7 failed (the live `login_failed` reseed failure, the tasks RESTRICT violation on reseed, dangling-label/ai_calls/extraction cases). After the fix: 25 passed in that file, plus the medical audit file (32 together). Cases: reseed after admin audit rows passes; reseed after finance/medical/AI/task/wish data leaves those tables empty (ai_calls kept) and audits OK; real user (`real@gmail.com`) with finance, medical, extraction, ai_calls and audit rows still fails the audit on each table, and a reseed keeps all of that user's rows while removing the synthetic ones; label/target/meta-email matrix for audit_logs; started_by dangling vs real.
Full Pest suite: 2648 passed, 1 failed (the test above, since updated; both files re-run green). `scripts/test-deploy-guards.sh`: 31 passed, GUARDS OK. Pint clean.
